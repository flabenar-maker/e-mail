# Стандарт заполнения модели письма

## Назначение и границы

Этот стандарт определяет точный перенос данных конкретного письма в существующую email model. Он применяется при новой сборке и к затронутой части design-dependent изменения. Он не требует чтения Figma для технической правки или read-only вопроса, не связанных с дизайном.

Порядок действий и разрешённые операции задаёт возвращённый workflow; маршрутизацию — skill. Стандарт не является дополнительным workflow, новым форматом письма или реестром компонентов.

## Входы и владельцы

- Один resolved bundle закреплённой версии системы содержит выбранные Mobile/Desktop contracts, foundations, этот стандарт и `email-model-schema`.
- Актуальные MCP-данные конкретной пары определяют состав, порядок, контент, состояния и изображения этого письма. Библиотечный пример не заменяет данные инстанса.
- Контракты определяют доступные элементы, свойства, слоты, вложенность и точный способ отображения. Геометрия, цвета, шрифты, отступы и responsive behavior не выводятся из текста описания и не копируются в модель как CSS.
- [JSON-схема модели](../schemas/email-model.schema.json) задаёт допустимые поля, типы и версию. Версия берётся из доставленной схемы, а не из памяти. Schema/semantic validation проверяет допустимость модели, но не доказывает совпадение с источником.
- [Стандарт экспорта](asset-export-standard.md), разрешённые asset contracts и foundations определяют подготовку файлов. Этот документ отвечает только за их связь с экземплярами модели.

При конфликте инстанса с contract факты повторно проверяются и сообщаются с точным node/полем/viewport. Контракт, дизайн и исходный контент не исправляются автоматически ради прохождения сборки.

## Identity и сопоставление двух версий

Компонент определяется зарегистрированными связями Figma file/main component/owner/variant с CUPIS ID. Имя слоя и Description не доказывают identity. В таблице соответствия сохраняются исходные instance node IDs обеих версий; сырой путь Figma не используется как model ID, если не соответствует схеме.

Одна пара логических экземпляров получает устойчивый уникальный `instance_id`. Повторения одного `component_id` в письме получают разные instance IDs. Сопоставление Mobile/Desktop подтверждается положением внутри конкретного владельца, зарегистрированной ролью/вложенностью и наблюдаемым содержимым. Один порядковый номер, одинаковый тип или похожий текст не доказывает, что это одна пара.

`element_id`, `slot_id`, `property_id` и `asset_contract_id` берутся из разрешённой записи соответствующего владельца. Связь с конкретным Figma-узлом подтверждается зарегистрированными variant/fact/nested связями и чтением инстанса. Нельзя угадывать ID по названию.

Если у двух версий разные element IDs, их значения связываются отдельно с точными IDs своей версии. Два одинаковых дочерних типа не объединяются и не меняются местами по одному `component_id`. Неоднозначная пара остаётся диагностикой с обоими node IDs, а не догадкой.

## Корень, порядок и вложенность

Модель содержит один root, соответствующий фактическому корневому шаблону письма. Его зарегистрированный контентный слот содержит разрешённые самостоятельные блоки в фактическом порядке. Список типов верхнего уровня не задаётся заново здесь: допустимость проверяется contract/placement правилами.

`slots` заполняет только элементы с режимом `slot`; порядок `instances` имеет значение. `nested_components` заполняет только объявленные владельцем элементы `nested-component`. Вложенная карточка, пункт, кнопка или бейдж не поднимается в корневой слот ради удобства.

Figma INSTANCE внутри границы изображения не становится отдельным model component: графика и её внутренние wrappers относятся к своему asset owner. Нельзя создавать model instance для каждого найденного Figma INSTANCE.

Структуры Mobile/Desktop читаются независимо. Нельзя автоматически складывать Desktop-колонки в Mobile или строить отсутствующую версию по аналогии. Отличие порядка/вложенности, не выражаемое текущими contracts и schema, сообщается как конкретный пробел представления.

## Заполнение существующих полей

| Поле | Что записывается |
|---|---|
| `id`, `metadata` | ID письма, язык и направление текста из подтверждённых входов; это не component facts |
| `root` | Корневой model instance |
| `instance_id`, `component_id`, `variants` | ID конкретного экземпляра, зарегистрированный компонент и селекторы Mobile/Desktop в форме схемы |
| `variant_axes` | При наличии дополнительных осей варианта — точные значения для Mobile и Desktop из конкретных инстансов (например, `Count: "2"` у NPS) |
| `property_values` | Записи `property_id + scope + value` с разрешённым типом |
| `visibility_values` | При отличии видимости конкретного узла — `element_id + scope + value` с boolean из подтверждённого источника |
| `content_values` | Записи `element_id + slot_id + scope + value`, где `value` имеет тип соответствующего content slot |
| `asset_files` | `asset_contract_id + path` на файлы данного экземпляра |
| `slots` | `element_id + instances` для упорядоченного наполнения слота |
| `nested_components` | Один логический `instance` на вложенный компонент: общий `element_id` либо `element_ids.mobile/desktop`, если ID позиции различаются |

Дополнительные оси варианта не кодируются в `variants` и не подменяются свойствами или внешним сходством. Если у выбранного инстанса есть оси помимо `Viewport`, заполняется `variant_axes.mobile` и `variant_axes.desktop` точными строковыми значениями из Figma; выбранный набор должен иметь соответствующий contract root. Для базового варианта без дополнительных осей поле не нужно.

Обязательные массивы присутствуют даже когда пусты. Нельзя добавлять произвольные поля модели, HTML, Figma dumps, contracts, repo SHA, параметры экспорта или verification statuses. Эти данные передаются соответствующими источниками/окружением/handoff.

Content/property/visibility bindings имеют `scope`. `asset_files`, `slots` и `nested_components` не получают выдуманный viewport scope. Если у одной логической вложенной позиции разные ID в Mobile и Desktop contracts, один `nested_components` binding задаёт `element_ids.mobile` и `element_ids.desktop` и один вложенный `instance`. Два экземпляра ради различия ID создавать нельзя. Оба ID подтверждаются конкретными Figma-узлами и выбранными contract roots.

Для одного ключа content/property/visibility нельзя одновременно писать `all` и viewport bindings, а также дублировать один и тот же scope. Для остальных bindings нельзя дублировать ключи, объявленные уникальными семантической проверкой.

## Значение scope

`all` допустим только когда одинаковы значение, тип и подтверждённая связь с целью в обеих версиях. Для content binding соответствующий element и content slot должны существовать с совместимым типом в обоих contracts. Совпадения строки недостаточно.

Во всех остальных случаях используются отдельные `mobile` и `desktop` bindings. Наличие элемента только в одной версии не разрешает `all`, даже если текущая проверка не обнаружила ошибку. Данные одной версии не подставляются в другую как неявный fallback.

## Текст, ссылки и alt

Текст переносится из фактических `characters`/text ranges без переписывания: сохраняются значимые пробелы, неразрывные пробелы, пунктуация и явные переводы строк. Визуальный перенос по ширине не становится символом перевода строки. Экранирование для HTML выполняет renderer; в модель передаётся текст, а не заранее экранированная разметка.

Тип значения соответствует content slot. В текущей схеме rich-text состоит только из text segments; произвольная inline-разметка не поддерживается. Значимые различия оформления диапазонов или встроенные ссылки не уплощаются молча: сообщаются range, требуемая семантика и недостающая возможность. Отсутствие ошибки JSON-схемы не подтверждает сохранение форматирования.

Ссылки берутся из данных конкретного письма, управляемого профиля или подтверждённого пользовательского ввода. При вёрстке запрашиваются только отсутствующие пользовательские URL видимых действий — одной формой с названием блока и фактическим текстом действия. Известные адреса и ссылки скрытых элементов повторно не запрашиваются. Обязательная отсутствующая ссылка блокирует выпуск; placeholder не выдаётся за извлечённый адрес.

Alt связывается с предназначением изображения и типизированным slot: decorative и informative значения не взаимозаменяемы. Существующий alt сохраняется. Для informative используется точный подходящий текст внутри экспортируемого узла или его владельца в конкретном письме; для decorative — пустая строка. Это разрешённое policy-derived преобразование, с указанием данного правила и конкретного исходного поля/диапазона; оно не объявляется непосредственно наблюдённым alt. Новые подписи не сочиняются и у пользователя не запрашиваются. Если исходный текст не прочитан, исследуется сам источник, а не запрашивается новый маркетинговый текст. Тема, прехедер и настройки отправителя также не являются полями опроса: уже известные значения сохраняются, отсутствующие не выдумываются и не блокируют саму вёрстку/ZIP.

## Свойства и видимость

Записываются фактические значения всех свойств, от которых зависят выбранная структура, видимость или содержание. `false`, пустая строка и отсутствие данных не эквивалентны. Нельзя использовать выражение «значение или default», теряя `false`, или считать отсутствие property выключенным состоянием.

Default используется только когда его применение подтверждено контрактом и состоянием инстанса; источник такого решения сохраняется. Фактический variant не выбирается по внешнему сходству и не подменяется библиотечным default.

Effective visibility отдельно для каждой версии объединяет видимость контракта, свойства, подтверждённое `visibility_values` и скрытых предков. Значение `true` не включает отключённое свойство или предка. `false` из конкретного макета может скрыть доступный `always` элемент библиотеки; это настройка экземпляра, а не изменение контракта. Скрытые вложенные позиции могут не содержать child instance, content, ссылки или assets. Если позиция видима только в одной версии, она сохраняет одну логическую пару и проверяется/рендерится только в этой версии. Невидимое поддерево не создаёт HTML или пустые зазоры, не входит в инвентарь ссылок и не требует экспорта; общий asset, используемый хотя бы в одной видимой версии, по-прежнему нужен. Каждая маска видимости проверяется по независимому графу источника и точному соответствию узла; произвольное исключение не заменяет это доказательство.

## Связь изображений с экземплярами

Для каждого файла сохраняется соответствие: model instance → asset contract → фактический Figma owner/source boundary → локальный файл. Изображение берётся из инстанса письма с его overrides, а не из main component.

Разные изображения повторений одного компонента не дедуплицируются по `component_id`. Общий Desktop asset для двух viewport применяется только при разрешённом контракте и подтверждённом соответствии пары. Различия источников, которые общий asset binding не умеет выразить, сообщаются, а не скрываются под одним файлом.

`path` — безопасный нормализованный относительный путь внутри `images/`; не абсолютный путь, не data URL и не ссылка за пределы результата. Basename содержит точный `asset_contract_id`, перед ним допустим префикс из строчных латинских букв/цифр с разделителями `-`, после него — необязательный числовой суффикс. Далее обязательны точные `profile.suffix` и `profile.extension` разрешённого export-профиля: например, `@2x` или `@4x` непосредственно перед расширением. Mobile/Desktop tag и произвольный instance ID в качестве суффикса не допускаются. Для повторений выбрать разные допустимые имена и сохранить точную связь с владельцем и export receipt; одинаковое имя не означает одинаковое изображение. Фактическое имя должно приниматься handoff, даже если файл уже существует.

Реальный receipt содержит связь с владельцем и фактическими экспортированными байтами. Запланированное имя файла не является экспортом.

Профиль, размеры, crop, alpha, фон, clipping и display behavior не определяются этим стандартом: они остаются в разрешённых asset contracts и foundations.

## Временная трассировка значений

Рядом с исходными MCP readings, но вне папки результата, ведётся проверочная таблица. Это evidence переноса, не второй формат письма и не runtime input взамен модели.

Каждая строка содержит:

- JSON pointer конкретного поля модели и model instance ID;
- viewport и связь пары; для `all` — подтверждение обеих версий;
- класс источника: Figma, явный user input, policy-derived либо contract/schema-derived;
- для Figma — file key, конкретный instance node ID, property/source path или text range, ссылка на raw reading и время чтения;
- для остальных источников — точный пункт пользовательского ввода либо source ID, путь поля и закреплённая версия правила/схемы/контракта;
- наблюдаемое значение, записанное значение и объяснение разрешённого преобразования, если оно было.

Для структуры фиксируются membership, порядок и parent/nested/slot связи, включая исключённые asset-internal узлы. Для автоматически назначенных model IDs фиксируется алгоритмическое соответствие экземплярам; они не объявляются исходными Figma IDs. Для assets указывается owner, export receipt и путь, а после экспорта — подтверждение фактического файла.

Сохранённая таблица не подтверждает саму себя: значение сравнивается с исходным чтением, а не с копией модели. Обрезанный ответ или пропущенный диапазон не является полным источником. При изменении макета повторно читается затронутая пара; данные разных состояний не смешиваются.

## Передача и критерий достаточности

Перед handoff модель и временная трассировка проверяются по [стандарту соответствия источнику](email-source-fidelity-standard.md). В существующий handoff передаются `repoRoot, model, candidates, assetEvidence, assetRoot`. `assetRoot` — корень, относительно которого разрешается `images/...`. Contracts, repo SHA и source trace не вкладываются в JSON model. Проверки и публикация выполняются в порядке workflow.

Модель достаточна для передачи, когда все выбранные contracts разрешены, структура и типизированные bindings валидны, каждому реализационно значимому значению соответствует подтверждённый источник, а все требуемые assets реально экспортированы и связаны с нужными экземплярами. Недостающие данные не заменяются библиотечными примерами.

Структурная валидность, source correspondence, asset verification и visual acceptance — разные результаты. Этот стандарт задаёт требования к переносу; отдельная проверка источника описана в `email-source-fidelity-standard`. Ни она, ни структурная проверка не подтверждают внешний вид письма.
