# Стандарт нейминга Figma email-библиотеки

Этот файл — единственный источник общих правил нейминга для Figma-компонентов, properties, структурных слоёв, export asset owners, библиотечных страниц, Sections, шаблонов и примеров CUPIS email-системы.

Стандарт определяет, как формировать и проверять имена. Он не перечисляет текущие компоненты и не заменяет реестр descriptions, Figma-дизайн, component Description или глобальную инструкцию по вёрстке.

## Область действия

Стандарт обязателен:

- для каждого нового компонента, variant property, component property, структурного слоя и asset owner;
- при явно разрешённом переименовании или перестройке существующего объекта;
- при naming-аудите библиотеки;
- при создании нового namespace или расширении контролируемого словаря.

Публикация стандарта сама по себе не разрешает переименовывать существующие компоненты. Существующие расхождения считаются legacy до отдельной команды на миграцию. Изменять Figma-имена, структуру, properties или bindings без прямого разрешения пользователя запрещено.

## Разделение ответственности

В этом стандарте находятся только универсальные naming-константы, словарь ролей, правила классификации и алгоритм проверки.

В реестре descriptions остаются:

- фактический перечень компонентов;
- точные component и variant IDs;
- текущие имена компонентов и variants;
- актуальные Description;
- состав библиотек и конкретные компонентные контракты.

В Figma остаются фактические слои, variants, properties, bindings, геометрия и дизайн. В глобальной инструкции остаются правила HTML, адаптивности, экспорта, форматов, crop, прозрачности и проверки готового письма. Точные размеры, padding, gaps, стили, export boundaries и исключения конкретного компонента находятся в его Description и реестре.

## Нормативные константы

~~~text
NAMING_LANGUAGE = English
COMPONENT_PATTERN = <Namespace>/<Semantic-Name>
COMPONENT_SLASH_COUNT = 1
COMPONENT_SEGMENT_CASE = Title-Kebab
LAYER_CASE = lower-kebab-case
PROPERTY_CASE = Title Case
REPEATER_INDEX = two-digit, starting at 01
VIEWPORT_PROPERTY = Viewport
VIEWPORT_VALUES = Mobile | Desktop
BOOLEAN_PROPERTY_PATTERN = Show <Role>
ASSET_SCALE_SUFFIX = @2x | @4x
ASSET_SUFFIX_POSITION = end
ASSET_SCALE_MUTATION = forbidden without explicit export-contract change
~~~

Title-Kebab означает: каждое смысловое слово начинается с прописной буквы, слова внутри сегмента разделяются дефисом. Утверждённые аббревиатуры сохраняют принятую запись, например NPS, QR или VK.

Не добавлять третий уровень через slash. Отличия layout, viewport, state, count, style или context выражаются properties, если объект сохраняет одну семантическую роль.

## Контролируемые namespaces

~~~text
Email
Banner
Block
Card
Item
Button
Badge
Details
NPS
Icon
Asset
~~~

Назначение namespaces:

- Email — части общей оболочки письма;
- Banner — крупные самостоятельные промо- и информационные модули;
- Block — самостоятельные контентные блоки;
- Card — повторяемые карточки внутри блоков;
- Item — вложенные строки, пункты и повторяемые элементы;
- Button — действия;
- Badge — живые компактные UI-элементы, не являющиеся экспортируемым изображением;
- Details — структурированные наборы реквизитов или данных;
- NPS — блоки оценки;
- Icon — переиспользуемый векторный glyph или знак; сам по себе не задаёт export boundary письма;
- Asset — публикуемая графика, экспортируемая как один визуальный asset.

Если ни один namespace не подходит, не изобретать новый в рамках компонента. Сначала обосновать новую системную категорию и отдельно изменить этот стандарт.

## Компонент или variant

Создавать отдельный компонент, только когда меняются семантическая роль, область применения или модель содержимого.

Использовать один COMPONENT_SET и variant property, когда различие относится к:

- Viewport;
- Layout;
- Style;
- State;
- Count;
- Context.

Не кодировать значения этих properties в имени компонента. Generic property Type не использовать для новых component sets: применять точное имя измерения.

Рекомендуемый порядок variant properties:

~~~text
Viewport
Layout
Style
State
Count
Context
~~~

Использовать только реально необходимые properties. Не создавать комбинации и controls «на будущее».

## Component properties

- Boolean property: положительная форма Show <Role>, например Show Caption.
- Text property: имя смысловой роли, например Heading, Body, Caption, Supporting Text или Button Label.
- Instance swap property: имя заменяемой роли, например Icon, Image или Button.
- Значения properties: полные английские слова в Title Case; числовой Count — цифрами.
- Одинаковое понятие во всех компонентах получает одно и то же имя. Не смешивать Type, Mode, View и Device для одного измерения.

Optionality определяется property, а не префиксом optional- в имени слоя.

## Структурные слои

Каждый слой, несущий структурный или смысловой контракт, получает имя. Внутренние слои используют lower-kebab-case и не используют slash.

Контролируемый базовый словарь:

~~~text
image-area
content-area
text-content
heading
body
caption
supporting-text
label
link
actions
cards
items
steps
bullets
rows
divider
social-links
background
glyph
artwork
~~~

Формы расширения:

~~~text
<role>
<role>-<qualifier>
<role>-<two-digit-index>
~~~

Правила:

- одинаковая смысловая роль имеет одинаковое имя во всех Mobile/Desktop variants, даже если меняются порядок, размер или направление Auto Layout;
- siblings с повторяющейся ролью получают стабильные имена item-01, item-02 или более точный эквивалент;
- индекс отражает порядок, а не текущий маркетинговый текст;
- не дублировать имя родительского компонента во всех дочерних слоях;
- не создавать дополнительный root-слой без отдельной layout-функции;
- layout-контейнер называть по функции, например image-area или content-area, а не wrapper или container;
- видимый divider остаётся слоем divider; пустые spacer-слои для отступов не создавать;
- Frame с Auto Layout использовать для структурных контейнеров;
- Group использовать только для неразделимой графики, где несколько shapes образуют одно artwork;
- Section использовать только для организации холста, навигации, review и handoff.

Запрещённые имена:

~~~text
Frame 12
Group 4
Rectangle 8
Wrapper
Container 2
Content Copy
Green Button
White Card
Desktop Image New
Mobile Text
~~~

Не включать в имя цвет, размер, padding, gap, позицию, текущее состояние макета или HTML-тег. Исключение — обязательный export scale suffix.

## Icon components

Переиспользуемые векторные знаки называются:

~~~text
Icon/<Semantic-Name>
~~~

Icon-компонент хранит glyph для повторного использования в других компонентах. Он не получает @2x/@4x только из-за того, что является графикой, и не считается export asset owner без отдельного export-контракта. Если письмо экспортирует внешний составной слой с этой иконкой, scale suffix остаётся на семантическом Asset owner, а вложенный Icon сохраняет имя без suffix.

## Asset owners и scale suffix

Внутренний semantic asset owner:

~~~text
<semantic-name> @2x
<semantic-name> @4x
~~~

Публикуемый атомарный asset component:

~~~text
Asset/<Semantic-Name> @2x
Asset/<Semantic-Name> @4x
~~~

Обязательные правила:

- suffix @2x или @4x находится строго в конце;
- suffix ставится на semantic asset owner, определяющий базовое имя файла;
- обычное переименование может изменить только semantic-name;
- существующий @2x обязан остаться @2x, существующий @4x обязан остаться @4x;
- изменение scale допускается только по отдельной команде, прямо меняющей export contract;
- не добавлять расширение файла в имя Figma-слоя;
- не добавлять Mobile или Desktop, если обе версии используют один asset;
- не переносить suffix на generic Vector, Group, Subtract, image-fill или другой вложенный технический слой;
- если Description задаёт отдельный export boundary, asset owner всё равно сохраняет semantic-name и scale suffix.

Связь имени слоя и базового имени файла:

~~~text
Figma: google-play-icon @4x
File basename: google-play-icon@4x

Figma: feature-image @2x
File basename: feature-image@2x
~~~

Формат файла, alpha, crop, display-size и способ экспорта определяются глобальной инструкцией и Description, а не этим стандартом.

## Mobile и Desktop

Viewport определяется property:

~~~text
Viewport=Mobile
Viewport=Desktop
~~~

Смысловые children обеих версий сохраняют одинаковые имена. Не использовать mobile- и desktop- в имени одного и того же элемента. Различия порядка или layout не создают новую смысловую роль.

Если конкретный элемент существует только в одном viewport, его имя всё равно описывает роль, например qr-code @4x, а не desktop-qr.

## Страницы, Sections, шаблоны и примеры

Страница получает короткое семантическое имя по своему назначению. Числовой префикс допустим только при нескольких равноправных библиотечных страницах, которым действительно нужна стабильная ручная сортировка. Для одной консолидированной страницы использовать имя без префикса, например `Email Components`.

Sections организуют холст и не меняют namespace компонентов. Их называют по функциональному семейству или области использования. Если имя Section создаёт бессмысленное дублирование с namespace дочерних компонентов, например `Icons/Icon` или `Assets/Asset`, использовать более широкое организационное имя, например `Shared`.

Повторно используемый assembly template может быть библиотечным component set, если его нужно регулярно вставлять как основу письма:

~~~text
Email/Template
Viewport=Mobile | Desktop
Content — SLOT
~~~

`Content` должен быть настоящим Slot-свойством Figma, а не обычным пустым Frame. Сам `Email/Template` не задаёт HTML-контракт: при вёрстке учитываются только помещённые в Slot компоненты и их собственные Description.

Разовый демонстрационный пример остаётся обычным top-level Frame:

~~~text
Example · <Family> · <Semantic-Name> · <Viewport>
~~~

## Алгоритм для нового объекта

1. Определить, является ли объект публикуемым компонентом, variant, вложенным item, icon, asset, шаблоном или примером.
2. Если повторное использование не требуется, оставить Frame и не публиковать компонент.
3. Выбрать namespace по семантической роли.
4. Проверить, не описывается ли отличие существующим component set через Viewport, Layout, Style, State, Count или Context.
5. Сформировать COMPONENT_PATTERN и необходимые properties.
6. Построить внутреннюю иерархию из контролируемых ролей; добавлять qualifiers только когда они устраняют реальную неоднозначность.
7. Сохранить одинаковые имена одинаковых смысловых слоёв во всех variants.
8. Пронумеровать повторяющиеся siblings двухзначными индексами.
9. Для export asset определить semantic asset owner и сохранить конечный @2x или @4x.
10. До записи показать предлагаемое имя и дерево затрагиваемых слоёв; изменение Figma выполнять только в разрешённой области.
11. После записи проверить фактические names, properties, children и отсутствие побочных изменений.
12. Синхронизировать реестр и Description только там, где переименование изменило их фактическое содержание или ссылки на слои.

## Логика аудита и расхождений

- Новый объект: несоответствие стандарту нужно устранить до завершения задачи.
- Существующий объект в явно разрешённой naming-миграции: показать точное сопоставление old → new и связанные обновления.
- Существующий объект в области другой задачи: не переименовывать без разрешения; сообщить только о расхождении, способном повлиять на текущую работу.
- Legacy-объект вне области задачи: не менять и не расширять аудит автоматически.
- Description-only: не превращать задачу в naming-миграцию.
- Утверждение уровня «вся библиотека соответствует» требует полного сканирования обоих library roots.

При конфликте между фактическим именем Figma и реестром реестр сначала приводится к фактическому состоянию или исправляется в рамках явно разрешённого Figma rename. Стандарт не превращает предполагаемое будущее имя в текущий факт реестра.

## Изменение стандарта

Стандарт изменяется только при появлении общего правила, новой системной категории или доказанной неоднозначности алгоритма. Добавление одного компонента, его точных слоёв, размеров или исключений не является основанием переносить эти сведения сюда.

Изменение стандарта не запускает автоматическую миграцию библиотеки. Миграция требует отдельной области, карты old → new, проверки ссылок и прямого разрешения пользователя.

## Проверка

- [ ] Объект правильно классифицирован: Component, Variant, Item, Asset, Template или Example.
- [ ] Имя компонента соответствует Namespace/Semantic-Name.
- [ ] Namespace входит в контролируемый список; переиспользуемые glyphs используют Icon, экспортируемые составные изображения — Asset.
- [ ] Отличия viewport/layout/state/count не вынесены в отдельные имена без причины.
- [ ] Properties используют единый словарь и положительные Boolean names.
- [ ] Структурные слои названы семантически и одинаково между variants.
- [ ] Повторяющиеся siblings имеют стабильные двухзначные индексы.
- [ ] Нет generic-, visual-, HTML- и viewport-зависимых имён.
- [ ] Semantic asset owner имеет неизменённый конечный @2x или @4x.
- [ ] В имя Figma-слоя не добавлены расширение файла или Mobile/Desktop.
- [ ] Для переиспользуемого Email/Template используется Viewport component set и настоящий Content Slot; разовые примеры остаются Frames.
- [ ] Description и реестр синхронизированы только при фактической необходимости.
- [ ] Legacy и unrelated-объекты не изменены без отдельного разрешения.
