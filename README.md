# Email-система ЕДИНЫЙ ЦУПИС

Система помогает Codex собирать маркетинговые и сервисные письма по макетам Figma, проверять результат и поддерживать библиотеку компонентов.

**Актуальное состояние системы хранится в основной ветке [GitHub](https://github.com/flabenar-maker/e-mail).** Локально допускается точный снимок выбранного коммита для чтения и проверок. Правки системы публикуются в GitHub; готовые письма, изображения, заполненные формы и результаты тестов остаются в отдельных локальных папках.

## Как начать работу

В новом чате укажи репозиторий и нужное действие:

| Задача | Что написать Codex |
| --- | --- |
| Загрузить актуальный контекст | «Открой `flabenar-maker/e-mail` и ознакомься с проектом» |
| Подготовить среду на новом ПК | «Открой `flabenar-maker/e-mail` и восстанови рабочую среду проекта» |
| Собрать письмо | «Сверстай письмо по этим макетам Figma» и приложи ссылки на Mobile и Desktop |
| Исправить письмо | Укажи папку письма, проблему и нужный результат; для изменения дизайна приложи макет |
| Проверить или изменить библиотеку | Назови компоненты и точную область проверки или изменения |

Ознакомление означает чтение. Восстановление среды включает проверку подключений, обнаружения навыков и зависимостей по [инструкции bootstrap](bootstrap/README.md). Вход в аккаунты и замена уже установленных навыков имеют свои границы разрешения.

## Как устроена работа

[Маршрутизатор](.agents/skills/cupis-email-task-router/SKILL.md) выбирает один из двух навыков:

- [Сборка писем](.agents/skills/building-cupis-emails/SKILL.md): новое письмо, исправление готового или проверка конкретного письма.
- [Поддержка системы](.agents/skills/maintaining-cupis-email-system/SKILL.md): контракты компонентов, библиотека Figma, описания, нейминг и системные источники.

Навык закрепляет версию системы и получает контекст нужного маршрута. Правила и значения компонентов хранятся в структурированных источниках, а не копируются в инструкции навыка. Выбор исполнителя, независимой проверки и среды тестов принадлежит [политике выполнения](data/execution/policy.yaml); профиль пользователя и ПК переиспользуется без повторной диагностики перед каждым тестом.

Для выпуска письма в Альткрафт Codex сначала исследует макет и собирает недостающие параметры и ссылки в единую форму с русскими названиями. Незаданные обязательные ссылки блокируют выпуск. Результат — локальная версионная папка с HTML и изображениями; выпуск для Альткрафта также включает ZIP и служебные текстовые файлы. Состав выпуска и стандартные ссылки определены в [профилях доставки](data/delivery/profiles.yaml).

Figma хранит фактический дизайн. Новые или изменённые факты сначала проверяются в Figma, затем записываются в контракт и отражаются в производной документации. Запись в Figma требует разрешения на конкретную область изменения. Наличие контракта или завершённая миграция сами по себе не доказывают его совпадение с макетом.

HTML-рендерер использует структурированные данные. Автоматическая документация и Figma Description служат для чтения; автоматически собранные документы не редактируются вручную. `shared.yaml` описывает вспомогательные элементы и корневой Template: параметры оболочки берутся из Template, графика Shared проверяется в составе использующего блока.

## Проверки и команды

Команды запускаются в изолированном снимке точного коммита GitHub с Node 24 и зависимостями из того же lock-файла.

| Команда | Что делает |
| --- | --- |
| `npm run validate` | Проверяет данные, связи и собираемость маршрутов |
| `npm run generate:check` | Проверяет актуальность автоматической документации без записи |
| `npm run generate` | Пересобирает документацию после разрешённого изменения данных |
| `npm test` | Запускает все Node-тесты |
| `npm run verify` | Выполняет validation и полный набор Node-тестов |
| `npm run resolve:skill-context -- --route <route> --mode <mode>` | Получает контекст выбранного маршрута; остальные обязательные параметры задаёт навык |

Для документации достаточно проверок затронутой области. Изменения кода и контрактов проходят полный набор проверок на финальном коммите. При отсутствии npm/pnpm допускается прямой запуск того же Node-скрипта с зависимостями по тому же lock-файлу; результат помечается `direct-equivalent`.

Переносимые проверки привязаны к точному коммиту и выбранному набору задач. Облачный запуск разрешается только явным запросом и даёт отдельные отчёты; PR Checks их не заменяют. Недоступность Actions обозначается `CLOUD_WORKFLOW_NOT_READY`. Установленная среда, реальные письма и фактическое взаимодействие с Figma проверяются локально. Подробности — в [протоколе проверок](bootstrap/README.md#explicit-verification-workloads).

Успешные тесты не заменяют независимую содержательную проверку. Слияние PR и установка навыков требуют соответствующего разрешения.

## Границы системы

- Сборка использует зарегистрированные компоненты. Неизвестный компонент останавливает работу до регистрации; создание новых блоков и Web-выдача не входят в объём системы.
- Отсутствующий или недоступный источник из manifest не заменяется локальной, старой или предполагаемой копией.
- Браузерная проверка подтверждает браузерное отображение. Импорт, отправка и проверка в реальных почтовых клиентах требуют отдельной внешней проверки.
- Планы и [Legacy](Legacy/README.md) сохраняют историю и контрольные материалы; они не становятся активными источниками правил. Статус каждой работы и её завершения указан в roadmap.
