# Email-система ЕДИНЫЙ ЦУПИС

Система помогает Codex собирать маркетинговые и сервисные письма по макетам Figma, проверять результат и поддерживать библиотеку компонентов.

**Актуальное состояние системы хранится в основной ветке канонического GitHub-репозитория компании.** Его адрес указывается при выборе проекта; система не привязана к личному аккаунту. Локально допускается точный снимок выбранного коммита для чтения и проверок. Правки системы публикуются в GitHub; готовые письма, изображения, заполненные формы и результаты тестов остаются в отдельных локальных папках.

## Как начать работу

[Подробная инструкция для сотрудников](docs/user-guide.md) — первый запуск, сборка письма, заполнение формы, проверка результата и исправления. Для нового пользователя начни с неё.

В новом чате укажи репозиторий и нужное действие:

| Задача | Что написать Codex |
| --- | --- |
| Загрузить актуальный контекст | «Открой репозиторий по этой ссылке и ознакомься с проектом» |
| Подготовить среду на новом ПК | «Открой репозиторий по этой ссылке и восстанови рабочую среду проекта» |
| Собрать письмо | «Сверстай письмо по этим макетам Figma» и приложи ссылки на Mobile и Desktop |
| Исправить письмо | Укажи папку письма, проблему и нужный результат; для изменения дизайна приложи макет |
| Проверить или изменить библиотеку | Назови компоненты и точную область проверки или изменения |

Команда «Ознакомься с проектом» загружает актуальный контекст для чтения. Команда «Восстанови рабочую среду проекта» включает проверку подключений, обнаружения навыков и зависимостей по [инструкции bootstrap](bootstrap/README.md). Вход в аккаунты и замена уже установленных навыков имеют свои границы разрешения.

## Как устроена работа

[Маршрутизатор](.agents/skills/cupis-email-task-router/SKILL.md) выбирает один из двух навыков:

- [Сборка писем](.agents/skills/building-cupis-emails/SKILL.md): новое письмо, исправление готового или проверка конкретного письма.
- [Поддержка системы](.agents/skills/maintaining-cupis-email-system/SKILL.md): контракты компонентов, библиотека Figma, описания, нейминг и системные источники.

Навык закрепляет версию системы и получает контекст нужного маршрута. Правила и значения компонентов хранятся в структурированных источниках, а не копируются в инструкции навыка. Модель выбирает пользователь. [Политика выполнения](data/execution/policy.yaml) подбирает только поддерживаемое усилие этой модели с запасом качества; исполнители и независимые проверяющие сохраняют её. Профиль пользователя и ПК переиспользуется без повторной диагностики перед каждым тестом.

Для выпуска письма в Альткрафт Codex сначала исследует оба макета и запрашивает только недостающие пользовательские ссылки в единой форме с русскими названиями. Для исходных Desktop и Mobile ссылок используются два отдельных поля. Тексты берутся из письма; вопросы об alt, теме, отправителе и модели не задаются. Скрытые элементы конкретного письма исключаются из соответствующей версии HTML, списка ссылок и необходимых изображений. Незаданные обязательные ссылки блокируют выпуск. Результат — локальная версионная папка с HTML и изображениями; выпуск для Альткрафта также включает ZIP и служебные текстовые файлы. Состав выпуска и стандартные ссылки определены в [профилях доставки](data/delivery/profiles.yaml).

Figma хранит фактический дизайн. Новые или изменённые факты сначала проверяются в Figma, затем записываются в контракт и отражаются в производной документации. Запись в Figma требует разрешения на конкретную область изменения. Наличие контракта само по себе не доказывает его совпадение с макетом: важны точные источники и границы проведённой сверки.

HTML-рендерер использует структурированные данные. Автоматическая документация и Figma Description служат для чтения; автоматически собранные документы не редактируются вручную. `shared.yaml` описывает вспомогательные элементы и корневой Template: параметры оболочки берутся из Template, графика Shared проверяется в составе использующего блока.

## Проверки и команды

Команды запускаются в изолированном снимке точного коммита GitHub с Node 24 и зависимостями из того же lock-файла.

При первой настройке нового профиля Codex один раз уточняет, сколько локальных Node-тестов запускать параллельно: 2 или 4, если вы ещё не сделали выбор. 2 уменьшает нагрузку на ПК. Уже выбранное число сохраняется в test_concurrency для доверенной пары «пользователь + ПК» и используется в следующих запросах; повторных вопросов и диагностики перед тестами нет. Существующий legacy-профиль без этого поля читается как2 без автоматической записи.

Чтобы явно изменить следующий выбор, скажите «переключи тесты на 2» или «переключи тесты на 4». Codex сохраняет его через init-execution-profile.mjs --action set-concurrency с прежней доверенной привязкой, без повторного сбора оборудования. Уже разрешённый запуск сохраняет своё число в frozen decision; новый выбор относится к следующим запросам. В результате каждой локальной Node-проверки указывается фактическое число.

Новые чаты читают сохранённый профиль один раз. В старых закреплённых задачах (pinned) перед использованием настройки нужно обновить source и context системы до поддерживающей её версии; публикация сама по себе не обновляет все открытые чаты.

| Команда | Что делает |
| --- | --- |
| `npm run validate` | Проверяет данные, связи и собираемость маршрутов |
| `npm run generate:check` | Проверяет актуальность автоматической документации без записи |
| `npm run generate` | Пересобирает документацию после разрешённого изменения данных |
| `npm test` | Запускает все Node-тесты с legacy default2; для4 передаётся local repository-full decision |
| `npm run verify` | Выполняет validation и полный набор Node-тестов с тем же decision/default2 |
| `npm run resolve:skill-context -- --route <route> --mode <mode>` | Получает контекст выбранного маршрута; остальные обязательные параметры задаёт навык |

Для штатной локальной проверки Codex передаёт frozen decision и сохранённый wrapper с постоянным runner_lock_root в `node scripts/run-verification.mjs --decision DECISION --profile PROFILE_READ_JSON` вместе с request ID, exact SHA, выбранными workloads и новой папкой evidence. Один тяжёлый batch, deadline30 минут и аппаратные пороги сохраняются; GitHub-hosted команды остаются на2. Прямой диагностический `npm test -- --decision DECISION` или `npm run verify -- --decision DECISION` может использовать4 только для local repository-full decision и не заменяет блокировку штатного runner.

Для документации достаточно проверок затронутой области. Изменения кода и контрактов проходят полный набор проверок на финальном коммите. При отсутствии npm/pnpm допускается прямой запуск того же Node-скрипта с зависимостями по тому же lock-файлу; результат помечается `direct-equivalent`.

Проверки привязаны к точному коммиту и выбранному набору задач. В этой рабочей среде проверки и регрессии выполняются локально; GitHub служит источником системы и площадкой PR. Облачный запуск разрешается только явным запросом и даёт отдельные отчёты; PR Checks их не заменяют. Недоступность Actions обозначается `CLOUD_WORKFLOW_NOT_READY`. Установленная среда, реальные письма и фактическое взаимодействие с Figma проверяются локально. Подробности — в [протоколе проверок](bootstrap/README.md#explicit-verification-workloads).

Успешные тесты не заменяют независимую содержательную проверку. Слияние PR и установка навыков требуют соответствующего разрешения.

## Границы системы

- Сборка использует зарегистрированные компоненты. Неизвестный компонент останавливает работу до регистрации; создание новых блоков и Web-выдача не входят в объём системы.
- Отсутствующий или недоступный источник из manifest не заменяется локальной, старой или предполагаемой копией.
- Браузерная проверка подтверждает браузерное отображение. Импорт, отправка и проверка в реальных почтовых клиентах требуют отдельной внешней проверки.
- Состояние системы подтверждается текущими источниками и результатами проверок точного коммита. Работы сверх согласованной области требуют отдельного задания.
