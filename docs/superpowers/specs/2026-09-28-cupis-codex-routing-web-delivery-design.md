# CUPIS: маршрутизация задач Codex и выдача письма в вебе

Статус: решение и implementation plan согласованы; пакет A в реализации на отдельной candidate branch. Пакеты B/C не начаты. Актуальность: 1 октября 2026 года.
Основание: согласованное в чате направление после завершения этапа 10.
Репозиторий: `flabenar-maker/e-mail`, исходный `main@189deb50904128f84601b5cfbcf607b247d5d5bb`.

## Цель и границы

Codex должен сам определять, какой существующий CUPIS-навык нужен для запроса, без просьбы пользователя угадывать его название. Это касается Codex в локальной среде и Codex в вебе; обычный ChatGPT не входит в объём. По результату сборки в вебе пользователь получает скачиваемый самодостаточный пакет письма, а не только PR или путь во временной среде.

Новый верхнеуровневый навык не становится третьим владельцем правил. Он отвечает лишь за выбор направления и передачу задачи:

| Намерение запроса | Передача |
| --- | --- |
| Создать, изменить или исследовать конкретное письмо | `building-cupis-emails`; дальнейшие route/mode определяются этим навыком и manifest |
| Проверить или изменить библиотеку, её компоненты, контракты, инструкции, синхронизацию; спросить о миграции | `maintaining-cupis-email-system`; paused-гейты остаются в силе |
| Спроектировать новый блок | Сообщить, что отдельный маршрут этапов 11–12 ещё не активен; не выдавать обслуживание библиотеки или сборку письма за этот маршрут |
| Неясно, новое письмо или изменение готового; неясна предметная область | Запросить только недостающее различие до записи |
| Явно совмещены письмо и библиотека | Разделить области и зависимость; не выполнять запись одного типа работы по полномочиям другого |

Явное указание пользователем одного из действующих специализированных навыков сохраняется. Маршрутизатор не отменяет прямой выбор пользователя и не создаёт альтернативный набор правил.

## Источники и исполнение

`system/manifest.yaml` остаётся единственным каталогом routes, bundle profiles и repo-scoped skills. Маршрутизатор использует только идентификаторы навыков и правила выбора; он не содержит Figma node IDs, component facts, точных размеров, CSS, HTML, asset-профилей, файловых списков или копии workflow. Router закрепляет текущий cloud `main` (или явно разрешённый candidate-test SHA) до чтения manifest и выбранного навыка. Специализация сохраняет переданный SHA без повторного выбора `main`; прямой вызов специализации закрепляет его самостоятельно. Несовпадение источников с выбранным SHA останавливает работу. Специализированный навык по-прежнему запрашивает ровно один resolved context bundle на этом SHA и исполняет возвращённые шаги. Недоступный или остановленный маршрут нельзя обходить ручной сборкой.

Для выдачи в вебе используется **тот же** путь: подтверждённые Figma-инстансы → resolved bundle → временная модель → действующий renderer → проверки → чистая версионная папка. Меняется только способ передачи уже проверенного результата. Локально остаётся папка `<slug>_<major>.<minor>/email.html` и `images/`. В вебе после того же gate рядом с версионной папкой создаётся ZIP с `email.html` и `images/` в корне архива; файл доступен пользователю для скачивания. Версионное имя находится в имени архива, а не добавляет третий объект внутрь.

ZIP не является источником правил, новой моделью письма или запасным рендерером. Он не хранится в системном GitHub. Исходная версия письма при continue/fix остаётся неизменной; результат получает следующий номер с шагом 0.1. Для веб-изменения существующего письма входом служит скачанный ранее пакет с проверенным версионным именем; произвольный набор файлов без ясной версии требует уточнения. Дизайн-зависимое изменение всё равно требует точной Mobile/Desktop-пары.

Пакет выдаётся только после успешной проверки. Содержимое: ровно `email.html` и файлы под `images/`; все локальные `src` доступны по относительным путям внутри ZIP, нет временной модели, логов, evidence или скриншотов. Архив не содержит абсолютных путей, переходов `..`, symlink, повторных имён или ссылок наружу. При неполном выводе пакет не создаётся и успех не заявляется.

## Поверхности и возможность выполнения

Официальная документация подтверждает обнаружение repo-scoped навыков в `.agents/skills` и рекомендует короткие описания и контекстный `AGENTS.md`: [Build skills](https://learn.chatgpt.com/docs/build-skills), [OpenAI Developers](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra). Но она не доказывает, что конкретная веб-задача имеет одновременно GitHub, Figma MCP, Node 24, локальную файловую среду и интерфейс выдачи ZIP. Поэтому веб-готовность требует реальной проверки в Codex Web, а не вывода из локальных тестов. При отсутствии любого обязательного средства задача получает явный blocker, без приблизительной вёрстки или публикации письма в репозиторий.

## Не входит

Не изменяются Figma, дизайн, structured component contracts, foundations, HTML-ядро, renderer templates, визуальные размеры, завершённые письма, пути текущих локальных результатов или paused-статусы. Не начинается этап 11 и не создаётся навык разработки новых блоков. Не внедряется отдельный сервис или CRM-отправка.

## Критерий готовности

Из чистого контекста в локальном Codex и реальном Codex Web корректно выбирается специализация для конкретного письма и для работы с библиотекой; неоднозначный запрос не вызывает запись. Локальная сборка остаётся побайтово/визуально эквивалентной там, где входы не менялись. Веб-сборка использует существующий renderer и отдаёт проверенный скачиваемый ZIP; распакованный пакет проходит локальные проверки `src` и структуры. Веб continue/fix создаёт новую версию и сохраняет входную. Все системные проверки идут локально на точном cloud commit, без GitHub Actions/PR Checks; визуальное сравнение и обычные тесты выполняет Terra Medium.
