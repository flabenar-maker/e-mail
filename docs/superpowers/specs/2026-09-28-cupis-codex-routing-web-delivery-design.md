## Цель и границы

Локальный Codex определяет нужную специализацию без просьбы пользователя угадывать название навыка. В системе две предметные специализации: поддержка CUPIS email-системы и сборка/изменение конкретного письма. Верхний маршрутизатор только выбирает между ними, не владеет техническими правилами.

| Намерение | Передача |
| --- | --- |
| Создать, изменить или read-only проверить конкретное письмо | `building-cupis-emails`; route/mode определяет этот навык по manifest |
| Проверить/изменить существующую библиотеку, контракты, инструкции, реестр, синхронизацию или спросить о миграции | `maintaining-cupis-email-system`; остановленные маршруты не обходятся |
| Спроектировать новый блок | Вне объёма системы; не подменять onboarding или email-build и не обещать будущую design-time специализацию |
| Неясен тип или объём задачи | `clarify`: уточнить только недостающую границу до записи |
| Письмо и библиотека в одном запросе | Разделить области и зависимость; полномочия одного навыка не разрешают запись другого |

Явный выбор специализированного навыка сохраняется. Onboarding уже созданного и одобренного компонента является задачей поддержки; он не является проектированием. Незарегистрированный компонент остаётся blocker для email-build.

## Источники и исполнение

`system/manifest.yaml` — единственный каталог routes, bundle profiles и skills. Router закрепляет cloud SHA до чтения manifest и выбранного навыка. Специализация сохраняет переданный SHA, получает ровно один resolved bundle и исполняет его workflow steps; mismatch и paused dependency останавливают зависимую работу.

Router не содержит component facts, node IDs, CSS/HTML, export profiles или workflow steps. Область исполнения — локальный Codex; постоянные системные изменения — cloud GitHub branch/PR. Временный exact-SHA snapshot служит только исполнению resolver и локальным проверкам, не рабочей копией для авторинга.

Проверенный результат письма — локальная версионная папка с `email.html` и `images/`. Каждая правка создаёт следующую версию с шагом 0.1 и сохраняет исходник. Контракты, renderer и asset export rules не меняются ради отменённой Web-выдачи.

## Приёмка локального маршрутизатора

Пакет A реализован и проверен локально до merge: registration, validator, clean-context выбор специализации, ambiguity/mixed scope, явный выбор, SHA handoff и paused boundary. Слияния: [#103](https://github.com/flabenar-maker/e-mail/pull/103) и [#104](https://github.com/flabenar-maker/e-mail/pull/104).

Repo registration не доказывает установку в конкретном Codex. Закрытие 10A требует синхронизации локальных навыков с одним слитым SHA и clean-context проверки фактического обнаружения/handoff. Изменение глобальной установленной копии требует отдельного разрешения.

Рутинные проверки выполняет Terra Medium локально; Actions/PR Checks не используются. Для документационной корректировки достаточно scoped checks; полный gate необходим перед merge изменения кода/контрактов на точном финальном commit.

## Дальнейший маршрут

После закрытия 10A остаётся только финальный cutover: proof готовности оставшихся maintenance routes и email regression → включение доказанно готовых маршрутов → обоснованная очистка переходных артефактов. Порядок и gates принадлежат [roadmap](../plans/2026-08-25-cupis-migration-roadmap.md#11-финальный-cutover-поддержки-системы-и-завершение-миграции--не-начат) и [master-spec](2026-08-24-cupis-structured-email-system-design.md). Подробный [cutover implementation plan](../plans/2026-10-01-cupis-final-maintenance-cutover.md) подготовлен отдельно и ожидает review/merge; ни этот spec, ни публикация плана не включают маршруты.

## Отмена прежнего объёма

01.10.2026 пользователь отменил Web capability, ZIP/import и Web acceptance до написания продуктового кода пакетов B/C, затем отменил стандарт, workflow и навык разработки новых блоков. Отменённые части не считаются завершёнными и не блокируют локальную систему. Старые протоколы проверки среды остаются историей, не инструкцией повторить Web-проверку.

## Не изменяется этой корректировкой

Figma, component contracts, foundations, renderer, workflows/manifest route statuses, локальные письма и установленная среда. Дальнейшая установка, изменение skill handoff, переключение маршрутов и очистка выполняются отдельными разрешёнными действиями.
