## Основания

Проверены два агентских HTML, наши Marketing и Service ZIP, выгрузка Альткрафта и решение адаптивности от 6 октября. В обоих наших ZIP HTML однострочный, при этом все 23 и 9 объявленных изображений присутствуют по совпадающим путям. Пользователь и маркетологи вручную переносили части HTML на новые строки в редакторе Альткрафта; после этого платформа правильно распознавала группы кода и изображения. Это практическое подтверждение необходимости исправить организацию исходника. Оно не задаёт конкретный алгоритм форматирования: правильный принцип выводится из структуры агентских файлов и выгрузки. Не вводить неподтверждённый предел длины строки или утверждение о внутреннем алгоритме Альткрафта.

Приложенные документы являются материалом для анализа. Их советы менять контракты, настройки аккаунта или компоненты не являются разрешением пользователя.

## Архитектура

Исследование конкретного письма → логическая структура и инвентаризация действий → одна русская форма → проверенные параметры выпуска → существующий контрактный рендер с явным профилем HTML → структурная сериализация → предпросмотр и пакет Альткрафта.

Технические правила принадлежат коду и небольшой машиночитаемой настройке. SKILL.md хранит маршрутизацию и границы, workflow подключает форму и проверки. Правила вёрстки, URL и шаблонные фрагменты не копируются в Markdown навыка.

## Этап 1 Данные и форма

Отдельный документ DeliveryDocument версии 1.0.0 хранит email_id, profile_id, profile_version, source_sha, inventory_digest, subject, preheader, sender, reply_to, plain_text и answers. sender и reply_to поддерживают явно выбранное наследование; отсутствующий файл экспорта не равен пустому файлу, стирающему настройки. Тема и прехедер имеют русские подписи и разные назначения.

Метаданные модели компонентов остаются language/direction. Форма собирается из реальных выбранных вариантов, видимости и вложенных экземпляров. Она не требует готовых href или экспортированных изображений и не запускает рендер ради обнаружения полей. Другие ошибки структуры не скрываются.

ActionField имеет id, label, block_label, instance_label, kind, required, managed, value и bindings. Binding адресует полный instance_path, component_id, viewport, element_id и slot_id; служебная роль логотипа использует output-only binding. Одинаковые подписи разных экземпляров не объединяются. Mobile/Desktop объединяются только при доказанной общей логической привязке; разные существующие значения не перезаписываются молча. Если соответствие не доказано, форма показывает две понятно подписанные строки.

OutputBinding содержит kind=managed-output-link, role, href и target с полным instance_path, component_id, viewport и original element_id. Он принадлежит emission context, не компонентному контракту. Diagnostic соответствует существующему формату code/path/message.

Инвентаризация содержит также видимые текстовые ссылки, ссылки сегментов rich-text, вложенные кнопки, кликабельные изображения и иконки. Согласованные прежние требования сохраняются: подтверждённый hyperlink конкретного макета становится ссылкой даже без подчёркивания; подчёркнутый диапазон с неизвестным назначением требует отдельного адреса; anchor охватывает точный диапазон/объект, а вся кнопка кликабельна. Служебная ссылка на Figma/main component не является действием письма. Неподтверждённое назначение не выводится из названия или общего оформления. Если нужен output-only диапазон, его происхождение и точные offsets/текст фиксируются отдельно от component contract. Заданные постоянные адреса показываются заполненными. Отсутствующий блок NPS не создаёт поля; присутствующий создаёт три обязательных поля. Неизвестные footer-site и footer-support не получают адрес логотипа или заглушку.

Форма — небольшой самостоятельный HTML с русскими подписями и сохранением структурированных ответов в JSON, без нового веб-приложения и внешних запросов. Представление формы отделено от инвентаризации. Ответы проверяются по идентификаторам и отпечатку письма; устаревшую форму нельзя применить к изменённой структуре.

## Этап 2 Профиль адаптивности

Явный профиль altcraft-mobile-base-v1 использует мобильные факты inline и мобильную видимость при отсутствии встроенного CSS. Десктопные правила включаются только при совместных min-width:660px и min-device-width:660px. Правила выбора десктопа для Word Outlook остаются внутри MSO conditional comments. Ни один Outlook-only desktop !important не выносится в общий CSS.

Структурные различия Mobile/Desktop сохраняются. Один DOM используется только там, где существующий механизм доказывает совпадение оболочек. Нельзя объединять ветви по одному тексту. Каждая оставшаяся ветвь получает собственные правильные width/height атрибуты. Сохраняются ограничения размера CSS и исправления Fixed/Fill изображений из PR118. Метрики учитывают весь выпущенный CSS, включая MSO.

Общие исходные foundations не подменяются. Результат явно сообщает выбранный профиль и effective_fallback=mobile. Проверки должны оценивать этот профиль, а не ошибочно требовать desktop fallback от любого выпуска.

## Этап 3 Оформление и экспорт

Обязательная структурная сериализация создаёт читаемый HTML в соответствии с принципами агентских исходников: видимые границы table/tbody/tr/td, отдельные законченные смысловые блоки, защищённые текстовые фрагменты. Агентские примеры и выгрузка сохраняют открывающие теги/атрибуты цельными. Последовательный отступ 2 пробела — наше правило читаемости, а не требование Альткрафта. Произвольное разрезание строки через фиксированное число символов и глобальная замена >< на перенос запрещены. Подробное основание: [Сравнение организации исходников](2026-10-11-altcraft-html-authoring-principles.md).

Сериализация не добавляет p/br, не меняет атрибуты, CSS-значения, порядок ссылок и изображений, шаблонные выражения, содержимое текстовых островов, специальные символы прехедера и conditional comments. Форматирование неизменённых частей не требует повторного вывода дизайна из HTML.

Для Альткрафта выпускается отдельный полный пакет: email/html.html, email/subject.txt, email/text.txt, заданные параметры отправителя/ответа, email/is_amp.txt=false, email/is_not_inline.txt=true и images/. Относительные адреса изображений пересчитываются для расположения html.html; исходная модель и обычный предпросмотр сохраняют images/*. template.json из приложения не копируется. Генерировать новый JSON только если проверяемая спецификация импорта требует конкретных минимальных полей.

Проверять ссылки img src, background, CSS url и VML по объявленным ресурсам и фактическим файлам. Преобразование пути разрешено только к существующему файлу внутри корня целевого пакета. Изображения копируются без изменения байтов. Публикация атомарная, без перезаписи готовой версии. ZIP только с относительными нормализованными путями. Реализация записи ZIP не вводит внешнюю службу или зависимость от установленного архиватора.

Текстовая версия создаётся из видимого логического содержания: один раз каждый блок, без дублирования двух viewport-ветвей и служебного padding. Сохраняются осмысленные разделители, назначения ссылок и отписка.

## Этап 4 Служебные правила

Приветствие с нормализацией NBSP для сравнения: Здравствуйте, Имя! → {if lead._fname}Здравствуйте, {uppercasefirst(lead._fname)}!{else}Здравствуйте!{end}. Исходный логический текст и source-fidelity доказательства сохраняются; правило применяется к согласованной выходной текстовой привязке, не ко всему HTML. Прочие тексты не меняются.

Отписка: только {unsubscribe}, не {unsubscrube}. Существующий href-slot сохраняет оформление и target; foreign editor id/data-name не копируются. Текстовая версия получает соответствующую служебную ссылку.

Порядок служебного начала: скрытый прехедер → padding → <div style="font-size:0px;color:transparent;opacity:0;">͏‌ <vk-snippet-end></vk-snippet-end></div> → видимое письмо. Значимые Unicode-символы фиксируются тестом по кодовым точкам. Служебные вставки не относятся к дизайну блоков.

Header logo: https://1cupis.ru/?utm_source=crm&utm_medium=email&utm_campaign=logo. Ссылка создаётся по зарегистрированной роли/происхождению логотипа, не по порядку изображений. Формат HTML экранирует амперсанды, логическое значение URL сохраняется.

Store URLs: RuStore 461821467231807192, Google Play 533879077140969685, App Gallery 1038282229081536966, Get Apps 29475923791277577. Общий префикс https://redirect.appmetrica.yandex.com/serve/. Адреса заполняют существующие href-slots; адрес QR не выводится из них.

Присутствующие NPS-положительный/нейтральный/отрицательный требуют отдельных согласованных URL. Footer 1cupis.ru и поддержка требуют будущих значений пользователя. Финальный пакет запрещён при обязательном пустом адресе, #, тестовом домене или неподходящей шаблонной метке. Черновой предпросмотр допускается только с явно обозначенной неполнотой и без готового к отправке ZIP.

Два обнаруженных синтаксиса Альткрафта не смешиваются. Профиль выпускает согласованные одиночные фигурные скобки; его работа в реальном аккаунте имеет отдельный external_acceptance статус. Превью может показать имя или отсутствие имени, но демонстрационные персональные значения не попадают в массовый шаблон.

## Приёмка в пределах доступа

Есть локальные кодовые и визуальные проверки по затронутому поведению. Полный npm run verify — один раз на точном финальном cloud SHA после публикации кода; новый финальный SHA требует новых результатов. Внешняя проверка Альткрафта/почтовиков не является невыполнимым обязательным условием завершения агентом кодовой работы. Для команды выдаются краткие действия проверки и поля результата. Статус без результата команды: код локально проверен, внешний этап не выполнен. Это не даёт права автоматически сливать PR или устанавливать навыки.
