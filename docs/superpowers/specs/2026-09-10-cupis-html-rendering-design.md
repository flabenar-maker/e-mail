# CUPIS HTML Rendering Design

Дата: 2026-09-10.

Статус: архитектура согласована; пакеты 1–9 реализованы, Package 10 расширен обязательным client-resilience контуром.

## 1. Назначение

Документ фиксирует целевую архитектуру детерминированной сборки CUPIS HTML-писем из фактических Mobile- и Desktop-инстансов Figma и структурированных component contracts.

Система не преобразует произвольный Figma-макет в HTML и не угадывает назначение неизвестных слоёв. Она собирает письмо только из зарегистрированных компонентов с машинно-проверяемыми контрактами.

Цели:

- получать повторяемый `email.html` без ручной доводки нового письма;
- сохранять фактический дизайн и явную Mobile/Desktop-логику;
- использовать одни component data для документации, проверки и рендеринга;
- блокировать неизвестную или неоднозначную семантику;
- не превращать design-time правила библиотеки в свободу выбора при HTML-сборке.

## 2. Границы

Система выполняет разрешение инстансов, построение временной модели, HTML-рендеринг, подготовку assets, проверки, постобработку и атомарную публикацию результата.

Система не выполняет:

- универсальный импорт произвольной Figma-структуры;
- автоматическое исправление Figma-дизайна;
- хранение конкретных писем в системном репозитории;
- обязательное тестирование каждого письма во внешних сервисах;
- ручную правку сгенерированного нового письма как штатное завершение сборки.

## 3. Основной поток

```text
Фактические Mobile/Desktop-инстансы Figma
                    ↓
Resolved component contracts и foundations
                    ↓
Временная нормализованная модель письма
                    ↓
Общий contract-tree interpreter
                    ↓
Email-примитивы и специальные обработчики
                    ↓
Временная сборка и проверки
                    ↓
Атомарная публикация email.html + images/
```

Одинаковые входы и версии источников должны давать одинаковый результат.

До получения полного bundle агент выполняет read-only подготовку входов: закрепляет cloud SHA и manifest, проверяет выбранный route и получает через MCP identity корня и компонентов дерева модели конкретной пары письма, включая вложенные компоненты, объявленные контрактом владельца. Вложенные asset wrappers и графика относятся к зарегистрированному export owner, а не становятся самостоятельными resolver candidates. Сопоставление с зарегистрированными canonical owners выполняется по точным identity/variant-связям, не по Description или визуальному сходству. Только подтверждённые component IDs поступают в resolver.

После разрешения действует один bundle. Если фактический состав компонентов уточнился, новый bundle полностью заменяет предыдущий на том же закреплённом SHA. Подготовка входов не разрешает экспорт, запись HTML или использование неразрешённых component facts. Для technical continue/fix она не вводит обязательного Figma-чтения.

## 4. Единственные владельцы данных

| Область | Владелец | Запрещённое дублирование |
|---|---|---|
| Общие исполняемые правила HTML | structured rendering foundation | component records и Core prose |
| Структура и свойства компонента | `data/components/*.yaml` | Figma Description и renderer code |
| Типографика | typography foundation | component prose |
| Отступы при разработке библиотеки | spacing foundation | HTML renderer |
| Source/export/display assets | assets foundation и component asset contract | отдельный renderer-словарь |
| Связь компонента с рецептом/обработчиком | renderer registry | повторное поле в component record |
| Объяснение нормативных принципов | разделённый Core | точные structured definitions |
| Порядок действий | workflow | component facts и foundations |

Figma Description остаётся компактной вспомогательной проекцией и не является входом HTML-рендеринга.

## 5. Rendering foundation

Новый машинно-проверяемый foundation хранит только общие исполняемые определения:

- канонический CUPIS breakpoint;
- допустимые responsive-стратегии;
- правила email-примитивов;
- безопасную постобработку;
- минимальный support profile.

Точные константы хранятся один раз. Core объясняет их назначение, но не создаёт вторую исполняемую копию.

Foundation не содержит component IDs, Figma node IDs, контент писем и карту частных исключений.

## 6. Временная модель письма

Модель существует во время текущей сборки и не становится постоянным реестром. Её единственный формат задаёт `schemas/email-model.schema.json`. Правила заполнения и трассировки принадлежат [Core-стандарту заполнения модели](../../../core/email-model-assembly-standard.md); workflow доставляет стандарт и существующую схему в одном email bundle.

JSON-вход содержит `schema_version`, `id`, `metadata` (язык и направление текста) и `root`. Дерево экземпляров содержит `instance_id`, `component_id`, Mobile/Desktop `variants`, `property_values`, типизированные `content_values`, `asset_files`, упорядоченные `slots` и, когда требуются, `nested_components`. Связь model instance IDs с фактическими Figma node IDs сохраняется отдельно: сырой instance path Figma не обязан соответствовать синтаксису model ID.

Ответственность остальных данных разделена:

| Данные | Владелец/передача |
|---|---|
| Геометрия, типографика, отступы, visibility и responsive semantics | Разрешённые component contracts и foundations закреплённого repo SHA; не копируются в model |
| Формат, crop, export/display/alpha параметры изображения | Component asset contract и assets foundation; model содержит asset contract ID и путь файла |
| Версия папки результата и закреплённый repo SHA | Окружение сборки и verification evidence; не дополнительные поля JSON model |
| Raw MCP readings, correspondence и источники контента | Временное verification evidence вне папки результата |
| Экспортные receipts и байты файлов | `assetEvidence` и `assetRoot` в handoff; `assetRoot` — корень, относительно которого существуют пути `images/...` |

Существующий handoff принимает `{ repoRoot, model, candidates, assetEvidence, assetRoot }`. `candidates` выводятся из проверенной component map. Resolver, handoff и renderer читают файлы из `repoRoot`: перед вызовом исполнитель обязан подтвердить соответствие этих файлов закреплённому cloud SHA. Для разрешённого candidate E2E используется временный изолированный exact-SHA снимок только для проверки, не локальная рабочая копия. Если соответствие среды не подтверждено, запуск останавливается с объяснением. Автоматическая runtime-проверка SHA этим описанием не вводится. Рендерер не читает Figma и не принимает произвольный HTML.

Агент заполняет модель по фактическим входам в шаге workflow построения модели. Отдельный автоматический Figma compiler не является обязательным prerequisite. Компонентные значения не восстанавливаются по памяти, из generated Markdown или Figma Description; невыразимое различие между инстансом и контрактом требует диагностики вместо придуманного override.

Прохождение schema/semantic/handoff проверки подтверждает допустимость данных, но не само по себе их совпадение с Figma. Evidence сопоставления и визуальная проверка подтверждают перенос по своим границам. Добавление workflow input не означает, что field-level source comparison уже автоматизирован.

Model и raw evidence не сохраняются в системный репозиторий. Model остаётся единственным входным форматом композиции: снимок Figma служит источником проверки, а не обязательным форматом будущего веб-редактора. Хранение документов и иной путь получения assets такого редактора проектируются отдельной задачей.

Для воспроизводимости `email.html` может содержать невидимый build metadata comment с версией renderer и вычисленным digest. Отдельный служебный файл рядом с письмом не создаётся.

## 7. Компонентный рендеринг

### 7.1. Покрытие

Каждый используемый `component_id` должен иметь зарегистрированное renderer coverage. Неизвестный или неготовый компонент блокирует сборку.

Coverage не означает отдельный HTML-модуль для каждого компонента.

### 7.2. Общий интерпретатор

Обычные компоненты собираются общим интерпретатором существующего contract tree. Он понимает только утверждённые semantic roles и render modes: presentation table, HTML text, HTML link, nested component, direct image, background image, slot и Figma-only source.

Факт принадлежит узлу, поведением которого управляет. Корневые безымянные факты вида `description-N` не являются renderer-ready состоянием.

### 7.3. Email-примитивы

Интерпретатор использует небольшой набор проверенных примитивов:

- оболочка письма и секция;
- table, row и cell;
- текст;
- ссылка и кнопка;
- direct/background image;
- responsive visibility wrapper;
- spacer только там, где он выражает точный контракт.

Примитивы владеют низкоуровневыми email-совместимыми шаблонами. Контракты не копируют их HTML.

### 7.4. Рецепты и исключения

Если дерева недостаточно, компонент получает небольшой декларативный рецепт композиции. Рецепт не повторяет размеры, контент и asset-параметры контракта.

Отдельный код допускается только когда поведение невозможно выразить деревом, примитивами и рецептом. Для такого обработчика требуется:

1. доказать недостаточность декларативной модели;
2. не расширять общую schema частным исключением;
3. зарегистрировать обработчик в едином renderer registry;
4. добавить контрактные и визуальные тесты.

Общий layout-pattern выделяется только после нескольких подтверждённых одинаковых случаев, а не заранее.

## 8. Responsive-поведение

Responsive-решение может относиться ко всему компоненту, секции или поддереву. Поддерживаются:

- общее дерево с разными значениями;
- viewport-specific узел или поддерево;
- независимые Mobile и Desktop contracts при реальном структурном различии.

Стратегия не угадывается по внешнему сходству. Breakpoint берётся только из rendering foundation.

Fallback без embedded CSS, минимальная поддерживаемая ширина, CSS budget, document metadata, alt semantics и dark-mode policy определены в [CUPIS Email Client Resilience Design](2026-09-16-cupis-email-client-resilience-design.md). Эти свойства проверяются до расширения coverage на остальные компоненты.

Обязательные защиты:

- обе версии разрешаются до рендеринга;
- ширина адаптивного изображения не меняется независимо от высоты;
- фиксированная высота не вводится без контракта;
- одна viewport-структура не создаётся автоматически из другой.

## 9. Текст и контент

Высота текста по умолчанию определяется содержимым. Фиксированная высота допустима только при явном безопасном контракте.

Минимальные типы контента:

- plain text;
- ограниченный rich text;
- URL;
- служебный placeholder;
- alt text;
- число.

Rich text не принимает произвольный HTML. Его словарь определяется после инвентаризации реального форматирования и содержит только подтверждённые inline-сегменты.

Неразрешённый тип или отсутствующее обязательное значение блокируют сборку.

## 10. Assets

Renderer использует существующие assets foundation и component asset contracts, а не вводит параллельную классификацию.

Раздельно разрешаются источник, export boundary, масштаб, формат, alpha/background, crop, proportions, display mode и Mobile/Desktop display sizes.

Обязательные ограничения:

- общий визуальный asset может использовать один файл для Mobile и Desktop, если таков контракт;
- `@2x` сохраняет intrinsic proportions, а адаптивная ширина использует автоматическую высоту;
- `@4x` сохраняет PNG и заданный alpha/background contract;
- искусственная подложка не добавляется;
- скругление HTML-контейнера не запекается в asset;
- карточная композиция экспортируется только по явной boundary;
- Figma asset извлекается через MCP из конкретного инстанса или явно разрешённого источника.

## 11. Renderer registry и digest

Renderer registry — единственное место связи `component_id` с общим интерпретатором, рецептом или специальным обработчиком. В component record не добавляется дублирующий renderer ID.

Render-impact digest вычисляется автоматически только из данных, влияющих на HTML:

- contract tree, render modes и visibility;
- properties и variants;
- asset contracts и dependencies;
- связанные исполняемые foundation definitions;
- рецепт или версия специального обработчика.

Purpose, документационный текст и Figma Description в digest не входят, если не меняют implementation semantics. Digest не редактируется вручную. Его изменение требует повторной проверки renderer coverage.

## 12. Атомарная сборка

Сначала результат создаётся во временной области. До публикации проверяются:

- регистрация и renderer-readiness компонентов;
- variants, properties и обязательный контент;
- assets и локальные `src`;
- Mobile/Desktop-поведение;
- безопасность постобработки;
- состав итоговых файлов.

Только после успешных проверок публикуются `email.html` и `images/`. Ошибка не изменяет предыдущую версию письма. CONTINUE/FIX сначала создаёт новую локальную версионную папку по действующему workflow.

## 13. Постобработка

Разрешены только заранее определённые безопасные операции: CSS inlining, нормализация атрибутов, удаление технических маркеров и финальная проверка путей.

Постобработка не угадывает свойства, не меняет структуру и размеры компонента и не скрывает renderer error.

## 14. Диагностика

Ошибка имеет стабильный тип, компонент и путь до значения. Минимальные классы:

- unknown component;
- incomplete contract;
- unresolved variant/property;
- unsupported responsive structure;
- missing/incompatible asset;
- invalid content type;
- stale renderer coverage;
- unsafe postprocessing;
- output publication failure.

Пользователь получает простое объяснение проблемы и требуемого исправления. Ошибка не запускает автоматическую Figma-мутацию.

## 15. Проверки

Обязательны:

- schema, semantic и dependency validation;
- renderer registry coverage;
- запрет ручных digest и дублирующих владельцев;
- renderer-ready facts;
- тесты всех ветвей properties и критических сочетаний;
- детерминированность HTML;
- табличная структура, пути, размеры и пропорции изображений;
- эталонные Mobile/Desktop-сценарии representative-компонентов и письма.

Полный перебор свойств используется только для небольшого числа комбинаций. Browser comparison проверяет геометрию, но не доказывает поддержку всех почтовых клиентов.

Litmus, Email on Acid и CRM-тесты остаются опциональными. Отдельные хаки для старого Outlook не входят в обязательный baseline без отдельного решения.

## 16. Пилот

До полной миграции архитектура доказывается на разных типах:

- `Email/Template` — корневая оболочка и Slot;
- библиотечная кнопка — properties и nested component;
- `Card/Image` — адаптивное direct image;
- `Banner/Secondary` — различное Mobile/Desktop image behavior;
- `Banner/App-Download` — сложная responsive-композиция;
- `Email/Footer` — текст, ссылки, иконки и переключаемые секции.

Только успешный пилот разрешает миграцию остальных активных компонентов.

## 17. Последовательность этапа 8

1. Characterization baseline и владельцы данных.
2. Rendering foundation и renderer-ready schema.
3. Семантическая нормализация пилотных contracts.
4. Разделение Core без копирования structured definitions.
5. Email-примитивы, interpreter и renderer registry.
6. Pilot coverage и только необходимые специальные обработчики.
7. Нормализованная модель, CLI и атомарная публикация.
8. Render-impact digest и типизированная диагностика.
9. Автоматические HTML- и контрактные проверки.
10. Client resilience 10A–10D и затем Mobile/Desktop visual scenarios.
11. Миграция остальных компонентов.
12. Shadow comparison и перевод workflows без одновременной подачи legacy/new правил.

Figma, production-письма и maintenance skill не переключаются скрытно. Figma требует отдельного MCP impact gate, а maintenance skill переводится на итоговые bundles отдельным этапом roadmap.

## 18. Критерии готовности

Этап завершён, когда:

- Package 10A–10D завершены, target-client fallback выбран по Altcraft evidence и зафиксирован в rendering foundation;
- все активные компоненты имеют renderer-ready contracts и coverage;
- стандартные компоненты собираются общим интерпретатором;
- исключения обоснованы и протестированы;
- rendering foundation/schema проходят validation;
- Core не дублирует structured definitions;
- workflow использует только новый набор источников;
- Mobile/Desktop-сценарии проходят проверки;
- новое письмо атомарно собирается в `email.html` и `images/`;
- comparison не показывает необъяснённых смысловых потерь;
- Figma и production-письма не изменены техническим cutover.

## 19. Зафиксированные решения

При обычной реализации не пересматриваются:

- contract-driven архитектура вместо arbitrary Figma-to-HTML;
- временная нормализованная модель;
- общий interpreter как основной путь;
- специальные обработчики только для доказанных исключений;
- единый владелец renderer mapping;
- автоматически вычисляемый render-impact digest;
- responsive-семантика на уровне нужного поддерева;
- повторное использование assets foundation;
- атомарная публикация;
- отдельные режимы NEW BUILD и CONTINUE/FIX.

Реальное противоречие сначала оформляется как архитектурное решение, а не локальное исключение.
