## Цель и согласованное поведение

Сотрудник открывает локальный `form.html`, видит недостающие адреса в порядке блоков письма, вставляет URL и скачивает `delivery.json`. У формы фиксированный программный шаблон. Уже полученных модели письма, профиля доставки и inventory достаточно; для подготовки формы не нужны дополнительный вызов нейросети, повторное чтение Figma или рендер письма/превью.

- Убрать видимые подписи экземпляров и технические ID.
- В «Текст кнопки» выводить точную надпись кнопки, для текстовой ссылки только её подчёркнутый фрагмент.
- Компактная локальная HTML-форма по блокам/порядку письма, только недостающие адреса.
- Повторяющиеся действия остаются отдельными; Mobile/Desktop различаются только при отдельных bindings.
- Фиксированный программный шаблон; без дополнительной работы нейросети, нового чтения Figma/превью.
- `delivery.json` сохраняет точную привязку ответов и существующие проверки.

## Что есть в закреплённом исходнике

`collectEmailActions({ model, componentIndex, profile })` в `scripts/lib/email-action-inventory.mjs` обходит выбранные Mobile/Desktop контракты, исключает невидимые действия, создаёт bindings и идентификаторы полей, объединяет только доказанно общие цели и вычисляет `inventory_digest`. Сейчас `add()` часто берёт `actionText()` всего элемента. Для `html-link` с `href`, а также `html-text` с `link-N-url` или `help-url`, это может давать весь абзац вместо подчёркнутой ссылки. Ветка `output-range-link` использует `segment.characters`, который не обязательно совпадает с текущим содержимым модели.

Функция `ownerText()` уже умеет находить видимый заголовок владельца; `email-action-labels.test.mjs` проверяет разные заголовки карточек при одинаковом CTA «Подробнее». Но `block_label` — текстовая подпись, а не надёжная идентичность группы. Текущий обход передаёт подпись через nested descendants, а при переходе в slot descendant теряет её. Одинаковые названия разных блоков нельзя использовать как ключ группировки.

`renderDeliveryForm({ inventory, deliveryDraft })` в `scripts/lib/email-delivery-form.mjs` уже показывает только результат `missingDeliveryFields()`, экранирует HTML и встроенный JSON, сохраняет ответы локально и не делает сетевых запросов. Сейчас каждая ссылка оформлена отдельной крупной карточкой с видимой подписью «Экземпляр …». `createDeliveryDraft()` сохраняет ранее введённые answers только при совпадении `source_sha` и `inventory_digest`.

`scripts/prepare-email-delivery.mjs` блокирует выдачу при diagnostics, создаёт новую папку, не перезаписывает прежнюю, записывает `delivery.json` и `form.html`. `validateDeliveryDocument()` проверяет идентичность письма, профиль, digest, SHA, обязательность, неизвестные answers, managed URLs и безопасность адресов. Эти границы сохраняются.

Для соответствия сегментов важен действующий `richTextFromFacts()` в `scripts/lib/email-interpreter.mjs`: скалярное содержимое должно совпадать с source text; rich-text содержит по одному текущему run на каждый исходный styled segment. При выборе URL приоритет: output binding, затем `help-url`, затем `link-${index + 1}-url`. Индекс считается по всем styled segments, включая неподчёркнутые.

## Представление формы

Один заголовок страницы «Ссылки в письме» и инструкция «Заполните только недостающие адреса. Прикрепите скачанный delivery.json в чат, чтобы продолжить сборку письма.». Каждый структурный блок получает одну секцию с заголовком. Внутри компактные строки: «Текст кнопки», «Ссылка» и, когда это нужно, существующий короткий заголовок карточки как контекст строки. Технические пути, role IDs, field IDs, подписи «Экземпляр …» и прочие подписи на каждое действие не выводятся пользователю. Они могут присутствовать во внутреннем JSON и DOM-связях.

Иллюстративное содержимое, не реальное письмо:

```text
Ссылки в письме
Заполните только недостающие адреса. Прикрепите скачанный delivery.json в чат, чтобы продолжить сборку письма.

Карточки с изображениями
Первый бонус
Текст кнопки                         Ссылка
Подробнее                           [                         ]
Второй бонус
Подробнее                           [                         ]

Информационный блок
Текст кнопки                         Ссылка
«Помощь»                            [                         ]

Футер
Текст кнопки                         Ссылка
1cupis.ru                           [                         ]
службу поддержки                    [                         ]

Скачать заполненные ссылки
```

«Первый бонус» и «Второй бонус» берутся из видимых заголовков владельцев карточек. Если обе карточки имеют один и тот же заголовок, их действия всё равно остаются отдельными строками в исходном порядке; форма не придумывает названия вроде «Карточка 1». При отсутствии заголовка контекст не выдумывается и длинный абзац не подставляется. Название структурного блока берётся из `profile.block_labels`, с текущим коротким fallback «Блок N», если имени нет.

При двух отдельных целей для одного действия рядом с подписью появляются точные подсказки «Mobile» и «Desktop». При общем binding обеих версий подсказок нет. Для действия, видимого только в одной версии, подсказка не появляется автоматически: она нужна для различения соответствующих отдельных целей, а не для перечисления поддерживаемых устройств. Если после фильтрации осталась только одна pending строка из доказанно разделённой пары, она сохраняет свою подсказку; определять пары нужно до фильтрации. Не читать и не разбирать `instance_label` для этих подсказок.

На ширине 1280 px форма имеет максимальную ширину 880 px, компактные строки из двух колонок с постоянным промежутком 16 px, внешние поля 20 px, вертикальные поля строки 12 px. От 600 px и ниже строка перестраивается в одну колонку: текст, затем подписанное поле адреса; внешние поля 16 px. На ширине 360 px и при увеличении до 200% нет горизонтального скролла страницы, наложений и обрезанного текста. Длинные URL переносятся в своих областях, а ввод прокручивается внутри поля. Поле и кнопка имеют высоту не менее 44 px; текст страницы — не менее 16 px. Геометрия — шаблон формы, без попытки повторить дизайн письма.

«(обязательно)» / «(необязательно)» остаются доступными понятными индикаторами. Сохранение пустого обязательного адреса остаётся возможным, как сейчас: окончательную готовность проверяет сборка. Точный статус после скачивания: «Ответы сохранены. Проверка готовности выполняется при сборке письма.». При отсутствии pending адресов: «Все ссылки уже заданы. Сборка продолжается без дополнительных ответов.»; полей и кнопки сохранения нет.

## Точные подписи и неизменная адресация

Обычная кнопка получает точный текущий текст модели, включая регистр и пунктуацию. Название системной роли его не заменяет. Текстовая ссылка получает только относящиеся к её прежнему binding подчёркнутые фрагменты, а не окружающий абзац, старый contract text или описание роли.

| Путь действия | Основание подписи | Что сохраняется |
| --- | --- | --- |
| Кнопка `html-link` / `href` без inline underline-разметки | Текущий видимый текст кнопки | `slot-link`, slot, ID, адрес |
| Текстовая `html-link` / `href` с underline-разметкой | Только подчёркнутые фрагменты внутри этого действия | Один прежний href target, без дробления |
| `html-text` / `link-N-url` | Подчёркнутый segment N, N — индекс всех style segments | Прежний slot target, без слияния с соседним `link-M-url` |
| `html-text` / `help-url` | Все подчёркнутые runs, к которым существующий renderer применяет этот shared target | Один shared URL; допустимы несколько фрагментов |
| `output-range-link` | Текущий текст соответствующего исходного range | Прежние start/end, kind, ID; каждый прежний range остаётся отдельным |

Соседние styled runs могут составлять одну связанную фразу, если один существующий binding адресует их все. Они соединяются без вставок. Несмежные подчёркнутые фрагменты одного shared target показываются в одной строке, разделённые визуальным разделителем « · »; разделитель обозначает несколько фрагментов, промежуточный неподчёркнутый текст не попадает в подпись. Это не создаёт дополнительных actions. Разные targets не объединяются только потому, что runs смежные, имеют одинаковые подписи или одинаковое значение URL.

Источник текущего текста — existing plain/rich-text content binding нужного viewport. При rich-text проверяются число/порядок runs по styled segments; используются текущие `run.value`. При неизменном скаляре можно использовать доказанное соответствие source text и сегментов. JavaScript start/end трактуются как текущие contract offsets; их не пересчитывают и не заменяют поиском похожей подстроки. Суррогатные пары и переносы сохраняются, не режутся произвольно.

Если скаляр изменён и соответствие старых ranges не подтверждено, runs не совпадают по числу или диапазоны недопустимы/неоднозначны, возвращается ограниченная diagnostic `EMAIL_DELIVERY_LABEL_RANGE_AMBIGUOUS` с binding path и причиной. CLI останавливает выдачу новой формы существующим механизмом diagnostics. Не подставлять весь абзац, не выбирать первый похожий фрагмент, не запускать новый проход модели. Diagnostic не включает весь текст письма или приватные адреса.

## Структурные группы и контекст

В inventory допустимы внутренние поля `display_group: { id, label }`, `display_context: string` и `viewport_hint: 'Mobile' | 'Desktop' | null`. `display_group.id` — структурный путь владельца блока, не текст заголовка. Владелец — непосредственный содержательный блок внутри email root/контейнера размещения; карточки внутри блока карточек остаются в секции этого блока, самостоятельная карточка внутри root образует свою секцию. Идентичность и label секции передаются через оба вида descendants: nested-component и slot. Сам root «Письмо» не поглощает все содержательные блоки в одну секцию.

`display_context` хранит ближайший фактический видимый heading карточки/другого владельца действия. Дочерняя кнопка наследует его; повторное добавление того же заголовка исключается. Контекст не выводится повторно, если он уже является заголовком секции. `block_label` можно сохранить для текущих diagnostics и совместимости тестов. Не извлекать структуру из строки, разделённой « — ».

Порядок определяется структурным обходом выбранного письма и элементов контрактов; slot/nested children занимают место соответствующего элемента. Группировка не сортирует по label, ID, component ID или алфавиту. Одинаковые заголовки разных структурных блоков дают две секции; повторяющиеся actions не удаляются. Два viewport прохода не дублируют секции одного владельца. При fallback desktop-only блоки также получают своё положение, а не добавляются произвольно в конец всей формы.

## Совместимость и сохранение ответов

Схема delivery остаётся `1.0.0`. Новая presentation metadata не добавляется в delivery JSON. Формат IDs, доказательства объединения Mobile/Desktop, ranges, binding kinds, `required`, `managed`, role и значения known URLs не меняются ради внешнего вида. Изменение label/group metadata закономерно меняет `inventory_digest`; gates `source_sha` + digest сохраняются. Старые answers не мигрируют автоматически, даже если ID остался прежним. Уже известные адреса текущей модели и managed адреса профиля используются штатно. Изменение только HTML/CSS шаблона при том же inventory не должно менять IDs или digest.

`missingDeliveryFields()` продолжает исключать known, answered и managed адреса. Сохранение клонирует существующий draft, меняет только ответы pending полей по внутренним ID, обрезает внешние пробелы введённого URL и скачивает `delivery.json` с UTF-8 JSON и переводом строки. Все metadata и непоказанные answers сохраняют семантически равные значения после JSON-сериализации (deep equality), без требования совпадения форматирования. Два одинаковых captions с разными ID должны получить два разных введённых адреса.

## Доступность и безопасность

Секции имеют семантические заголовки; каждый input — уникальный `id` и явный `<label for>`, с доступным именем из действия, фактического контекста и viewport hint при наличии. Видимые заголовки колонок не заменяют label. Подсказка обязательности связана через `aria-describedby`. Tab идёт по полям в порядке письма, затем на кнопку; Enter сохраняет форму. Видимый focus не убирается. Статус — существующий `aria-live="polite"`.

Оставить `type="text"`: действующая проверка допускает `http`, `https`, `mailto`, `tel` и разрешённый managed token отписки; браузерная URL-проверка не должна сужать этот контракт. Финальная проверка URL, обязательных полей, managed override, source/digest mismatch, неизвестных IDs и metadata остаётся в `validateDeliveryDocument()`. Успех скачивания не обозначает готовность к выпуску.

Все caption/context/group/hint значения экранируются как текст; JSON внутри script экранирует `<`, `>` и `&`. Не применять `innerHTML` к вводу. Форма не включает remote scripts, шрифты, изображения, requests, аналитику или автоматическое открытие введённого адреса. Загруженный JSON создаётся через Blob/object URL, object URL освобождается после запуска скачивания. Тесты закрывают `</script>`, кавычки, `&`, Unicode и HTML-подобный текст. Только синтетические fixtures могут попасть в скриншоты/тесты/PR; реальные формы, адреса и письма не публикуются.

## Риски и границы

Основные риски: stale offsets при изменённом тексте; shared href на нескольких runs; потеря владельца через slot descendants; одинаковые заголовки разных блоков; ошибочная переадресация answers при переупорядочивании UI; ложное переиспользование старого digest. Для каждого есть критерий в матрице и задача в плане. Исправление caption не решает неоднозначность данных источника: такой случай должен остановиться с diagnostic.

Не входят: новые компоненты и контракты, изменения Figma, новые AI-проходы, миграция старых answers, переустройство renderer, инфраструктура, новые зависимости, модели/политики, импорт/отправка в Альткрафт и проверка почтовых клиентов. GitHub — источник и площадка PR; Actions и PR Checks не запускаются и не служат доказательством качества. Merge и установка этим документом не разрешены.
