# Сохраняемый выбор параллельности локальных тестов: 2 или 4

## Задание и граница текущего коммита

Пользователь 13 октября 2026 года попросил полностью спланировать возможность выбора 2 или 4, опубликовать план новым коммитом, провести независимое ревью и выполнять проверки планового изменения на 4. Уточнение пользователя: «Разовый выбор, который МОЖНО будет изменить в дальнейшем». Это сохраняемое предпочтение для существующей доверенной пары пользователя и ПК. Перед каждым прогоном вопрос не повторяется. Для этой среды пользователь уже выбрал 4; повторное подтверждение не нужно.

Этот коммит добавляет только данную спецификацию и план. Реализация, установка навыков, изменение рабочего профиля и слияние не выполняются. Шаги 11/12 плана #133 остаются в своей прежней области и состоянии.

Канонический репозиторий: `flabenar-maker/e-mail`. Закреплённый родитель текущего PR #134: `7f03aaf9e66afc79ad7321f7d120152b17af6cda`; его runtime/test база: `b766c52f639d45a3e098a00cfce2b80a3131673c`. Main на момент исследования: `b8ee255bde370a9b932cf36071904be771d86d8e`. Перед будущей реализацией заново закрепить разрешённую базу и проверить перечисленные интерфейсы; старые результаты не относятся к новому SHA.

## Почему одной инструкции недостаточно

На закреплённой базе `data/execution/policy.yaml` задаёт local/cloud/workload limits с concurrency 2; Node-команды полного и визуального наборов содержат `--test-concurrency=2`. `verification-runner.mjs` проверяет точное совпадение с BASE_LIMITS, а `execution-docs-check.mjs` отдельно создаёт дочернюю команду на 2. Строгие схемы фиксируют 2 и запрещают неизвестные поля. Профиль сохраняет базовые workload signatures; resolver сравнивает их и local_limits перед выбором цели. CLI runner сейчас использует профиль только для постоянного lock root. Прямой `npm test` вообще не задаёт явную параллельность. Их рассогласование может дать отказ runner, скрытый запуск на 2 или отчёт с чужой подписью.

## Решение

### R1. Один сохраняемый выбор

- Разрешены ровно целые числа `2` и `4`. В интерфейсе пользователя это «меньше нагрузка» и «больше параллельных проверок», без обещания конкретного ускорения.
- Выбор хранится как optional `test_concurrency: 2 | 4` в существующем профиле пары. Отдельного глобального файла настроек и повторной диагностики ПК нет.
- Новый интерактивный bootstrap спрашивает один раз при первичной настройке, только если пользователь ещё не указал значение. В этой среде уже данное указание 4 используется как вход настройки будущей реализации. Оно не записывается этим плановым коммитом.
- Старый валидный профиль без поля читается как 2 в памяти. Чтение ничего не дописывает, не спрашивает пользователя и не запускает collector. Старый API init без нового аргумента также сохраняет прежнее поведение с 2.
- Явное «переключи тесты на 4/2» вызывает атомарное изменение предпочтения. Это настройка следующих запусков, а не новая анкета на каждый запуск. Изменение сохраняет pair_key, initialized_at, observations, observations_status, baseline_policy_digest, workload_decisions и local_limits побайтно/по значениям без переоценки оборудования.
- Отсутствующий, повреждённый, чужой или недоступный для записи профиль не исправляется автоматически. Ошибка не является успешным сохранением настройки.
- Повторный init уже валидного профиля сохраняет выбор. Другой выбор в init не заменяет preference: возвращается typed conflict с указанием setter. Явный аппаратный refresh сохраняет preference, хотя обновляет аппаратный baseline по отдельному разрешению; read/refresh не принимают flag выбора. Setter использует только уже существующую active binding, не создаёт новую пару при её отсутствии.

### R2. Замороженный выбор для одного запуска

- Resolver получает предпочтение только из валидного профиля с доверенной привязкой пары и переносит его в limits выбранных локальных workloads. При отсутствии пригодного предпочтения применяется прежнее значение 2.
- Разрешение цели workload сначала проверяет базовую подпись из exact-source policy. Переключение 2/4 не пересчитывает аппаратные наблюдения, не делает неизвестный workload доверенным и не превращает известную локальную цель в cloud из-за новой effective signature.
- После resolution значение для данного request фиксируется. Последующее изменение сохранённого предпочтения действует на следующий request; уже начатый прогон и его acceptance продолжают использовать прежнее значение.
- CLI-флаг `--test-concurrency` — внутренний способ передать зафиксированное значение, а не обязательный вопрос пользователю. Несоответствие flag/decision запрещает запуск до spawn.
- Обычный пользовательский путь всегда читает сохранённый выбор и передаёт decision. Голый legacy `npm test` без контекста остаётся совместимым запуском на 2; он не является путём автоматического применения сохранённого предпочтения.

### R3. Actual commands и доказательства

- Один общий helper строит effective workload из канонической policy: для local разрешены 2/4, для github-hosted остаётся 2. Исходная policy, snapshot и список тестов не редактируются ради выбора.
- В Node-test argv допускается ровно одна контролируемая замена установленного флага. Для docs-scoped helper передаёт значение фиксированной программе `scripts/lib/execution-docs-check.mjs`, которая использует его в дочернем Node-test argv. Пользователь не задаёт shell, executable, произвольные команды или changed paths.
- Не-Node программы, browser worker counts, число агентов и число тяжёлых batches не изменяются этим выбором. Лимит 4 — верхний лимит Node test files, а не закрепление за CPU cores и не схема 4+1+1.
- Workload signature вычисляется по effective commands/requirements/limits. Для default 2 возвращается ровно прежняя структура, включая docs wrapper argv, поэтому прежняя базовая подпись 2 сохраняется. Для local 4 подпись отличается; cloud 2 не меняется.
- Decision, runner evidence, receipt и acceptance должны согласовать target, source SHA, request ID, effective signature и test_concurrency. Свежий успешный receipt 2 не закрывает decision 4 и наоборот. Изменение глобального предпочтения не делает старые receipts доказательствами нового запуска.
- В новых локальных результатах учитываемых Node workloads поле `workload_results[i].test_concurrency` выводится явно, отдельно для каждой mapped строки; поля общего выбора на root receipt нет. Другие workloads сохраняют прежнюю форму. Legacy receipt без поля допустим только как 2 при уже совпавших исходных identity/signature; поле не даёт права восстановить отсутствующую подпись или свидетельство.
- Receipt validator проверяет identity/coverage, а не истинность произвольного JSON. Actual child argv подтверждается принадлежащим runner запуском и реальными CLI-тестами; независимый reviewer читает bound command records. Совпавшая metadata не доказывает, что вручную сфабрикованный отчёт исполнил заявленную команду. В этом изменении второй универсальный verifier доказательств не создаётся.

### R4. Совместимость и неизменные ограничения

- Cloud limits, workflow carrier и cloud command argv остаются на 2. Local preference 4 не попадает в github-hosted signature/request. В этой среде проверки всё равно выполняются только локально; Actions/PR Checks не запускаются и не становятся доказательствами качества.
- `schema_version: 1.0.0` сохраняется. Новые поля optional, с enum 2/4; старые формы читаются new code как 2. Строгие additionalProperties и остальные проверки сохраняются. Старый pinned code не обязан читать профиль с новым полем: активные старые задачи обновляют source/context перед применением новой функции.
- BASE policy local_limits и workload limits остаются базовыми 2. Добавляется отдельное source policy `local_test_concurrency: { allowed: [2,4], default: 2, workload_ids: [docs-scoped, repository-full, visual-fixtures] }`; это разрешение bounded override для перечисленных Node-test workloads, а не увеличение всех остальных лимитов. Другие workloads сохраняют argv/limits2; mixed batch может содержать unchanged2 и selected4 rows. Если такого поля нет в legacy policy, разрешено только 2; сохранённое4 не применяется молча на2.
- Deadline всего batch — 30 минут; max_heavy_batches — 1. Сохраняются общий постоянный heavy lock, запрет автоматического захвата stale lock, подтверждение завершения owned process trees до освобождения lock, exact-SHA и same-lock dependency gates.
- Смена предпочтения использует существующий profile init.lock и atomicJson. Она не захватывает test heavy lock, не отменяет чужой запуск, не стирает init markers и не добавляет workload signatures.
- Модель выбирает пользователь; actual executor/reviewer сохраняют её. Routine tests и visual checks делегируются, independent reviewer отличен от executor.

## Данные эксперимента и пределы выводов

Локально на runtime SHA b766c52 один и тот же набор 126 тестов из 12 файлов прошёл при 2/4/6/4+1+1. Время: 267.58/183.15/184.93/193.75 секунды. Выбор 4 уменьшил время этого набора примерно на 32%; 6 и 4+1+1 дополнительного выигрыша не показали. Это одиночные последовательные замеры с возможным влиянием кеша и фона, а не результат полного набора. Частные local benchmark/profile files не публикуются.

## Приёмка будущей реализации

Обязательны actual local 2→4→2 round trip через сохранённый профиль → resolver → CLI runner → дочерние Node argv → receipt → finalizer, негативные значения и stale/mismatch cases; отсутствие collector calls; сохранение неизвестных workload guards, cloud 2 и heavy lock/deadline/process termination. Пользователь не получает повторных вопросов о выборе. Нужны exact final SHA local checks на выбранных 4 и независимое primary-source review. Полный runtime набор требуется после реализации, а не для публикации этого плана. Конкретные письма, Figma и внешняя почтовая приёмка в этот объём не входят.
