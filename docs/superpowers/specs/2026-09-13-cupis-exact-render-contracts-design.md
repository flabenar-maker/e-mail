# Точные render contracts и допустимая композиция компонентов

Дата: 2026-09-13. Статус: проектное дополнение к [архитектуре этапа 8](2026-09-10-cupis-html-rendering-design.md), ожидает проверки пользователем.

## Задача и установленная причина

Визуальная проверка пакета 10 показала письмо с системным шрифтом и стандартным цветом ссылок, неверными фонами и отступами, а также горизонтальное переполнение Mobile. При этом текущие Node/Windows-проверки PR #60 проходят. Причина — нарушение инварианта между структурированным component contract и HTML: `interpreter`-покрытие допускает неполные визуальные факты, часть фактов не потребляется renderer, а временная модель допускает внутренние компоненты напрямую в `Email/Template.Content`.

Конкретные подтверждения на текущем main: в пилотной модели `Card/Image` и `Button/Primary` стоят напрямую в корневом Content; `Block/Cards-Images` содержит ссылку на `Card/Image`, но ещё не renderer-ready; у текстовых узлов пилота есть отдельные размеры, но нет полных ссылок на typography foundation; у `Email/Footer` факт `email-wrapper-width=600px` ошибочно интерпретируется как ширина самого Mobile-футера. Описание некоторых Figma-компонентов использует «синий», «тёмный» или «примерно» там, где утверждается фактический визуальный параметр.

Этот документ уточняет контрольные границы уже согласованного Stage 8. Он не становится новым источником component-specific цветов, геометрии или типографики: их владельцы остаются прежними.

## Решение 1. Точный разрешённый контракт до HTML

Для каждого реально отображаемого узла в обоих viewport renderer получает нормализованный набор фактов. Значение считается разрешённым только если оно является типизированным точным literal с Figma provenance либо ссылкой на существующее точное foundation definition. Ссылка разрешается до рендеринга; неподтверждённое значение из Description, скриншота, названия слоя или сходного компонента не подставляется.

Полнота определяется по render mode и фактическому видимому состоянию:

- Видимый текст и текстовая ссылка: точный typography style ID или полный обоснованный component-specific literal; разрешённые family, weight, size, line-height и letter-spacing; точный цвет; применимые alignment и decoration. Невидимый текст не требует CSS.
- Presentation container: точные layout axis, gap, width/height behavior, padding, alignment, paint и clipping/radius там, где они влияют на результат. Фактическое отсутствие Fill не заменяется искусственным фоном; оно фиксируется как проверенное отсутствие paint.
- Direct image: конкретный asset contract, source/export boundary, display geometry либо `fluid width + auto height`, crop и presentation clipping. Адаптивное изображение не получает фиксированную высоту.
- Background image: конкретный asset contract, размер области, crop/position и текстовый эквивалент. Нельзя подменять direct image фоновым режимом.
- Nested component и slot: точная ссылка на дочерний component ID либо допустимые роли детей, viewport/property effects и порядок.

Для цветов, градиентов, размеров и отступов запрещены словесные суррогаты. Градиент хранит точный тип, направление и позиции/цвета stops отдельно от точного solid fallback. Примитив может предоставить общий default лишь тогда, когда он явно определён как исполняемая константа rendering foundation и не противоречит Figma; browser default не считается контрактом. Каждый render-impact fact должен иметь явного потребителя в renderer или проверке. Неизвестный, проигнорированный или конфликтующий факт блокирует `interpreter` readiness.

Проверка полноты применяется ко всем компонентам, которые могут попасть в HTML. `source-only` и `unsupported` остаются допустимыми статусами реестра, но не становятся renderable. До миграции остальных active-компонентов в пакете 11 их неполный контракт не превращается в «приблизительный» HTML: попытка использования завершается понятной ошибкой.

## Решение 2. Допустимая композиция письма

`Email/Template.Content` принимает только самостоятельные email-секции с явно разрешённой ролью. Внутренние `card`, `button`, `item`, `icon`, `asset` и сходные роли напрямую в Content не допускаются. Правило принадлежит контракту слота/общей семантике композиции, а не списку специальных запретов по component ID.

`Card/Image` размещается через объявленную ссылку `Block/Cards-Images.cards → Card/Image`; эта ссылка проверяется при разрешении модели. `Button/Primary` размещается внутри допустимого баннера или блока согласно его component-specific ограничению, а не самостоятельной секцией. Validator проверяет роль, фактический родительский слот и ожидаемый nested component ID до получения HTML. Ошибка содержит путь конкретного instance.

Пилотная модель пакета 10 пересобирается как валидное письмо: `Email/Template` содержит реальные секции; для проверки карточки и Primary в пилот заранее доводятся до renderer-ready их фактические родительские компоненты. Их Mobile/Desktop структуры не выдумываются по текущей HTML-картинке. Это переносит только необходимые зависимости из пакета 11 вперёд, но не отменяет миграцию всех остальных компонентов пакета 11.

## Решение 3. Граница renderer и владелец ширины

Renderer не трактует произвольный суффикс `-width` как ширину текущего элемента. Нормализованный факт должен называть объект и свойство, к которому относится. Ограничение максимальной ширины email-wrapper принадлежит `Email/Template`; футер занимает доступную ширину своего родителя. Mobile использует точное поведение из Figma и не получает фиксированные 600px на футере. Табличный примитив переносит применимые padding/align/paint на поддерживаемые email-элементы; он не оставляет критичные параметры на HTML-теге, где они игнорируются.

Для каждого видимого текста renderer выводит разрешённый font stack, weight, size, line-height, letter-spacing и color. Ссылка не наследует браузерный синий цвет. Контейнер без подтверждённого Fill остаётся без добавленной подложки. Если текущий primitive не может честно представить факт в email HTML, это отдельная диагностическая ошибка, а не молчаливое пропускание.

## Figma Description и источники

Полный контракт остаётся в `data/components/*.yaml` с точными foundation references и Figma provenance. Figma Description по действующему стандарту остаётся короткой проекцией и не становится вторым полным CSS-реестром. Если существующее Description говорит «синий», «тёмный», «примерно» или ошибочно называет внутреннюю карточку самостоятельной секцией, это metadata drift: при проверке исполнитель сообщает пользователю точное расхождение и предлагает синхронизацию. Само Description не участвует в HTML-сборке и не подменяет canonical record. Обычные числовые факты исправляются в canonical record; в Description остаются только действительно критические ограничения, выраженные без двусмысленности. Запись в Figma — отдельная разрешённая MCP-операция и не входит в этот PR.

## Проверки и границы выпуска

1. Тесты сначала воспроизводят нынешние ошибки: прямой `Card/Image` и `Button/Primary` в Content, неполный typography/paint/gradient, проигнорированный render-impact fact, Mobile footer 600px и отсутствующий padding на корректном table cell.
2. Schema, semantic/readiness validation и renderer выдают стабильные диагностические коды с component/viewport/element path. Неполная модель не публикует письмо.
3. Пилот сравнивается с фактическими Figma Mobile/Desktop вариантами по каждому компоненту; отдельная сборка проверяет правильную вложенность и ширину. Временные assets и screenshots остаются вне репозитория. Expected HTML фиксируется только после прохождения визуального gate.
4. Затем пакет 11 заполняет точные контракты и coverage остальных active-компонентов. Green CI без прошедшего визуального gate не считается готовностью пакета 10.
5. PR #60 остаётся draft до проверок. Production-письма, дизайн Figma, active route lists, maintenance skill и `main` не меняются этим исправлением. `docs/superpowers/plans/cupis-active-work-context.md` не обновляется без отдельной просьбы пользователя.
