# Переносимый контекст CUPIS email-системы — проект решения

Дата: 2026-08-19  
Статус: согласованная архитектура, ожидает утверждения перед реализацией  
Репозиторий: `flabenar-maker/e-mail`

## Цель

Сделать репозиторий самодостаточной точкой восстановления рабочего контекста Codex на другом компьютере. После открытия репозитория пользователь должен иметь возможность сказать одну из двух естественных фраз:

- «Ознакомься с проектом» — Codex только загружает и кратко пересказывает актуальный контекст;
- «Восстанови рабочую среду проекта» — Codex проверяет зависимости и безопасно подготавливает локальную среду.

Если репозиторий ещё не открыт, полная стартовая фраза должна быть такой:

> Открой `flabenar-maker/e-mail` и восстанови рабочую среду проекта.

Решение восстанавливает рабочий контекст проекта, но не историю исходного чата.

## Не входит в цель

- автоматический вход в GitHub или Figma вместо пользователя;
- хранение токенов, паролей, абсолютных локальных путей или идентификаторов локальных runtime;
- безусловная перезапись глобального `~/.codex/config.toml`;
- автоматическое включение `sandbox = "elevated"`;
- копирование конкретных проектов писем, `email.html`, `images/`, тестовых результатов и архивов;
- автоматическое изменение или публикация Figma-дизайна;
- жёсткая привязка к одной модели Codex как условию запуска.

## Основные решения

### 1. README — главный понятный человеку вход

Корневой `README.md` получает короткий раздел «Восстановление контекста». Он:

1. распознаёт две фразы пользователя;
2. направляет Codex к протоколу в `bootstrap/README.md`;
3. объясняет, что для первого запуска нужно сначала открыть репозиторий;
4. не дублирует email-правила, component contracts или maintenance workflow.

### 2. AGENTS.md — минимальный автоматический указатель

В корне появляется `AGENTS.md`, который применяется Codex при работе в репозитории. Он должен только:

- объявить `README.md` точкой входа для знакомства и восстановления;
- потребовать следовать `bootstrap/README.md` для setup-сценария;
- сохранить канонические роли файлов из корневого README.

Подробные правила в `AGENTS.md` не копируются, чтобы не создать второй источник истины.

### 3. Bootstrap-протокол — единственный источник setup-логики

`bootstrap/README.md` описывает два раздельных сценария.

#### Сценарий A: «Ознакомься с проектом»

Только чтение:

1. определить текущий SHA ветки `main`;
2. прочитать на одном SHA:
   - `README.md`;
   - `core/email-figma-prompt.md`;
   - `registry/email-component-descriptions-registry.md`;
   - `workflows/library-maintenance-checkpoint.md`;
3. прочитать `bootstrap/manifest.yaml`;
4. сообщить назначение проекта, доступные режимы, зависимости и ограничения;
5. ничего не устанавливать и не менять.

#### Сценарий B: «Восстанови рабочую среду проекта»

Разрешены только безопасные и обратимые setup-действия:

1. выполнить read-only сценарий;
2. проверить наличие обязательных GitHub и Figma возможностей;
3. установить или предложить установить отсутствующие плагины штатным способом Codex;
4. запросить у пользователя вход/подтверждение OAuth, когда этого требует GitHub или Figma;
5. проверить автообнаружение repo-scoped навыка;
6. сравнить переносимые рекомендации с локальной конфигурацией;
7. перед изменением конфигурации создать резервную копию, показать планируемую разницу и применить только отсутствующие безопасные ключи;
8. запустить `bootstrap/verify.ps1`;
9. сообщить, что готово, что осталось ручным и какие проверки фактически прошли.

Повторный запуск должен быть идемпотентным: он не создаёт дубликаты навыков, плагинов или настроек.

## Предлагаемая структура

```text
/
├── AGENTS.md
├── README.md
├── bootstrap/
│   ├── README.md
│   ├── manifest.yaml
│   ├── config.portable.toml
│   └── verify.ps1
└── .agents/
    └── skills/
        └── maintaining-cupis-email-system/
            ├── SKILL.md
            └── agents/
                └── openai.yaml
```

Существующий навык переносится из `skills/maintaining-cupis-email-system/` в `.agents/skills/maintaining-cupis-email-system/`, потому что `.agents/skills` — repo-scoped путь автообнаружения Codex.

Миграция должна одновременно обновить:

- ссылки и таблицу ответственности в `README.md`;
- путь в `.gitattributes`;
- bootstrap manifest и проверки;
- локальную установленную копию только в setup-сценарии, если она конфликтует с repo-scoped навыком.

Два одноимённых активных навыка оставлять нельзя. Repo-scoped версия является приоритетной; глобальная копия не должна автоматически перезаписываться или удаляться без явного подтверждения.

## Manifest

`bootstrap/manifest.yaml` — машинно-читаемая карта зависимостей и источников, а не копия правил. Минимальные поля:

```yaml
schema_version: 1
repository: flabenar-maker/e-mail
entrypoint: bootstrap/README.md

canonical_sources:
  - README.md
  - core/email-figma-prompt.md
  - registry/email-component-descriptions-registry.md
  - workflows/library-maintenance-checkpoint.md

skills:
  required:
    - path: .agents/skills/maintaining-cupis-email-system
      name: maintaining-cupis-email-system

plugins:
  required:
    - figma@openai-curated-remote
    - github@openai-curated-remote
  optional:
    - superpowers@openai-curated-remote

figma:
  file_key: 8zka5bHkcrJVK9I9dKjnhC
  roots:
    marketing: "538:17236"
    service: "538:17235"

portable_config: bootstrap/config.portable.toml
verification: bootstrap/verify.ps1
```

GitHub и Figma обязательны, потому что канонический процесс читает GitHub и при необходимости обращается к библиотеке Figma. Superpowers полезен для дисциплины планирования и проверки, но отсутствие этого плагина не блокирует работу email-системы.

## Переносимая конфигурация

`bootstrap/config.portable.toml` содержит только безопасные рекомендации проекта. Предлагаемые значения:

- включённый `multi_agent`, если функция поддерживается текущей версией Codex;
- рекомендуемый высокий уровень reasoning с допустимым fallback;
- комментарии о предпочтительной модели без жёсткого требования конкретного model ID.

Файл не содержит:

- секретов;
- абсолютных путей;
- локальных plugin cache paths;
- runtime IDs;
- OAuth-данных;
- обязательного elevated sandbox;
- полного снимка пользовательского `config.toml`.

Setup объединяет рекомендации с существующей конфигурацией, а не заменяет её. Неизвестные и пользовательские ключи сохраняются.

## Проверка

`bootstrap/verify.ps1` работает без изменения состояния и возвращает ненулевой код при обязательной ошибке. Он проверяет:

1. запуск из корня ожидаемого репозитория;
2. наличие всех файлов из manifest;
3. наличие ровно одного repo-scoped навыка с ожидаемым именем;
4. отсутствие старого дублирующего пути после завершённой миграции;
5. валидность ссылок между README, AGENTS и bootstrap-файлами;
6. отсутствие секретоподобных значений и абсолютных machine-specific путей в переносимой конфигурации;
7. согласованность repository, Figma file key и root IDs с каноническими источниками;
8. доступность PowerShell-команд без сетевых записей.

Сетевая часть bootstrap отдельно проверяет:

- read-доступ к `flabenar-maker/e-mail`;
- доступность GitHub-плагина;
- доступность Figma-плагина и read-доступ к указанному файлу/roots.

Проверка Figma остаётся read-only. Если OAuth не выполнен, результат помечается как ручной блокер, а не маскируется как успешный.

## Ошибки и остановки

Bootstrap останавливается без частичного изменения конфигурации, если:

- репозиторий или канонический файл недоступен;
- канонические файлы нельзя прочитать на одном SHA;
- manifest невалиден;
- существующий config нельзя безопасно разобрать или объединить;
- требуется установка/подключение, на которое пользователь ещё не дал подтверждение;
- обнаружены две конфликтующие активные копии навыка и нет разрешения выбрать одну.

Недоступность рекомендованной модели не является блокером: используется текущая совместимая модель, а ограничение указывается в отчёте.

## Безопасность изменений

Перед локальным изменением setup обязан:

1. показать точные файлы и ключи, которые будут изменены;
2. сохранить датированную резервную копию пользовательской конфигурации рядом с исходным файлом;
3. не печатать секретные значения в diff или отчёте;
4. применить минимальное слияние;
5. повторно разобрать итоговый TOML;
6. при ошибке восстановить исходный файл.

Установка плагина и OAuth рассматриваются отдельно: установка может быть предложена или запущена штатным механизмом Codex, но авторизацию подтверждает пользователь.

## Критерии приёмки

Реализация считается готовой, если подтверждены все сценарии:

1. В уже открытом репозитории фраза «Ознакомься с проектом» приводит к read-only отчёту без файловых и конфигурационных изменений.
2. В уже открытом репозитории фраза «Восстанови рабочую среду проекта» запускает bootstrap-протокол без необходимости указывать внутренний путь.
3. В пустом чате фраза «Открой `flabenar-maker/e-mail` и восстанови рабочую среду проекта» однозначно приводит к нужному репозиторию.
4. На чистой тестовой конфигурации setup предлагает обязательные плагины, корректно останавливается на OAuth и продолжает после подключения.
5. На существующей пользовательской конфигурации сохраняются неизвестные ключи, создаётся backup и применяется только минимальный diff.
6. Второй запуск не меняет уже готовую среду.
7. Repo-scoped навык обнаруживается без ручного копирования.
8. Проверка не требует Superpowers и не блокируется отсутствием конкретной модели.
9. Никакие email-правила, descriptions или component contracts не продублированы в bootstrap-файлах.
10. Figma, `main`, локальные письма и пользовательские секреты не изменены.

## Порядок реализации после утверждения

1. Составить отдельный пошаговый implementation plan.
2. Добавить bootstrap-файлы и минимальные указатели.
3. Перенести навык в `.agents/skills` и обновить все ссылки атомарно.
4. Добавить статические и PowerShell-проверки.
5. Выполнить read-only, clean-config и повторный idempotence-сценарии.
6. Проверить diff только по разрешённым путям и сохранность канонического содержания.
7. Обновить draft PR результатами проверок.
8. Не сливать PR в `main` без отдельного разрешения пользователя.

## Риски и ограничения

- Codex не может узнать о README репозитория, который ещё не открыт и не назван.
- OAuth GitHub/Figma принципиально требует участия владельца аккаунта.
- Интерфейсы установки плагинов могут различаться между Desktop и CLI; bootstrap должен описывать намерение и использовать доступный штатный механизм, а не хрупкий локальный cache path.
- Глобальные настройки принадлежат пользователю, поэтому безопасное слияние сложнее простой замены, но предотвращает потерю чужих настроек.
- Перенос навыка меняет структуру репозитория и должен выполняться одним согласованным изменением со всеми ссылками и проверками.
