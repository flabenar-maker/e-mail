# Ошибка привязки корневого слота Figma

Дата: 2026-10-12. Проверенная версия системы: `b8ee255bde370a9b932cf36071904be771d86d8e`.

## Результат разбора

Причина подтверждена на сохранённых данных конкретного письма и неизменённом коде основной ветки. Проверка видимости составляет неправильный идентификатор дочернего узла экземпляра Figma: соединяет владельца и библиотечный узел через `;`, пропуская начальную `I`. Корневые экземпляры письма имеют обычные числовые ID, а их дочерние узлы — составные ID с `I`.

| Версия | Корень конкретного письма | Библиотечный узел Content | Фактический ID из чтения Figma | Ожидает текущий код |
| --- | --- | --- | --- | --- |
| Mobile | `2021:4164` | `1103:7` | `I2021:4164;1103:7` | `2021:4164;1103:7` |
| Desktop | `2021:4163` | `1103:8` | `I2021:4163;1103:8` | `2021:4163;1103:8` |

Из-за этого правильное место верхних блоков не находится в фактической цепочке родителей. Возникают **26 `EMAIL_SOURCE_VISIBILITY_RELATION_MISMATCH`: 13 верхних блоков × 2 версии**. Заполненные ссылки и подготовленные изображения не исправляют это расхождение.

В этом PR сохраняются диагностика и план. Изменение рабочего алгоритма — отдельный этап после согласования плана.

## Где возникает ошибка

1. [email-source-visibility.mjs](../../../scripts/lib/email-source-visibility.mjs), `expectedNode()`, строки 20–32: обе ветки возвращают `owner + ';' + nativeNodeId`. Первая использует provenance фактов элемента, вторая — зарегистрированное доказательство `mobile-slot-background` / `desktop-slot-background` для геометрически пустого Content-слота.
2. В том же файле, строки 151–159, рассчитывается `expectedPosition` родительского элемента. Для связи `slot` код требует его точного присутствия среди физических предков дочернего экземпляра. Само требование корректно; рассчитанный ID не совпадает с исходным.
3. [email-source-fidelity.mjs](../../../scripts/lib/email-source-fidelity.mjs), строка 177, запускает эту проверку при экземплярных масках видимости. Она затрагивает все связи, а не только скрытые части письма.
4. [verify-email-source.mjs](../../../scripts/verify-email-source.mjs) возвращает код 1 и диагностику. [email-build-orchestration.mjs](../../../scripts/lib/email-build-orchestration.mjs), строки 412–449, превращает её в `source-evidence-mismatch`; `executeEmailBuildHandoff()` останавливается до вызова renderer, строки 538–544.

Значения `1103:7` и `1103:8` в зарегистрированных доказательствах правильные. Коррекция контракта, макета, модельных связей или captured ID не нужна.

В [figma-component-evidence.mjs](../../../scripts/lib/figma-component-evidence.mjs), `projectedNodeId()`, строки 632–638, уже есть рабочий алгоритм этой системы: один префикс `I` перед всей составной цепочкой, сохранение вложенного пути и точное сопоставление корня с его экземпляром. Его можно использовать как образец для узкой поправки валидатора видимости.

## Доказательства и границы

- Production CLI и `verifyEmailModelSource()` на неизменённом облачном коммите воспроизвели те же 26 диагностик, что сохранены при остановке письма.
- Для проверки причинности во внешней диагностической копии графа изменены только два ID Content-слотов и прямые ссылки на них как на родителей: они приведены к ошибочному ожиданию текущего кода. Диагностика исчезла. Это диагностический контрпример; такой изменённый граф нельзя использовать как доказательство соответствия Figma или как исправление письма.
- Контрольные варианты этого диагностического графа по-прежнему отвергают отсутствующий/дублированный слот, слот чужого владельца, перестановку Mobile/Desktop, блок вне точного слота, неверный owner/variant, изменённый порядок блоков, скрытый родительский слот и отсутствие зарегистрированного доказательства слота.
- **65 существующих локальных проверок прошли:** 62 проверки source fidelity, source CLI и экземплярной видимости; 3 выбранные проверки new-build handoff. Они не обнаруживают исходную ошибку. Внешние диагностические пробы описаны отдельно от этих тестов.
- Файлы конкретного письма сохранены локально; все восемь снятых контрольных сумм остались неизменными. Отдельный `model.json` семантически равен модели внутри source evidence. Отличие от старого model digest объясняется сериализацией: digest относится к `JSON.stringify()` встроенной модели, а не к форматированным байтам отдельного файла.
- Повторное чтение Figma и визуальная проверка в этом разборе не выполнялись. Указанные фактические ID взяты из сохранённого чтения исходного макета. Последующее разрешение продолжить тестовую сборку в исходном чате не означает, что исходная проверка прошла.

## Почему существующие тесты пропустили ошибку

`sourceScenario()` в [email-instance-visibility.test.mjs](../../../tests/rendering/email-instance-visibility.test.mjs) использует искусственные владельцы `m-root` / `d-root` и производные ID вида `m-root;11:1`. Такие данные повторяют формулу валидатора. Не проверяется сочетание настоящей формы числового корня Email/Template, составного Content-ID с `I` и включённой проверки видимости.

Тестам нужны независимые значения ожидаемых ID и физического графа. Конструировать новые ожидаемые данные через исправляемый helper нельзя: это снова позволит ошибке в алгоритме и тестовом источнике совпасть.

## Требования к исправлению

- Корневой элемент сохраняет исходный ID владельца без добавления `I`.
- Дочерний узел проецируется из точного владельца и полного зарегистрированного native ID: `I` появляется ровно один раз; вложенные пути обеих сторон сохраняются.
- Один маленький локальный helper используется в обеих ветках `expectedNode()`. Другой модуль аудита остаётся образцом; импортировать его целиком или проводить общий рефакторинг не требуется.
- Проверки file key, owner, main variant, viewport, физической цепочки родителей, порядка, own/effective visibility, полноты охвата и режима production сохраняются.
- Недоказанная проекция возвращает `null` и сохраняет блокирующую диагностику. Поиск по имени, суффиксу ID, похожему размеру, порядковому номеру и принятие двух вариантов ID запрещены.
- Сырые Figma ID, граф, correspondence, библиотечные доказательства, контракты и дизайн сохраняются. Система исправляет собственный расчёт, а не подменяет исходные данные.
