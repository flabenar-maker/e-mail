# CUPIS: заполнение модели письма и завершение Stage 10

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Routine local tests and visual regression must be delegated to `gpt-5.6-terra` with `medium` reasoning and bounded context.

**Goal:** Собрать два предоставленных пользователем письма существующим renderer из проверенных данных конкретных Figma-инстансов, проверить версионное изменение и завершить Stage 10 без зависимости от истории чата.

**Architecture:** Единственный формат композиции письма — существующий `email-model`. Codex получает факты конкретного письма через Figma MCP, сопоставляет их с разрешёнными контрактами и заполняет модель. Существующие validators, handoff и renderer выполняют проверку и HTML-сборку; evidence переноса данных остаётся отдельным временным материалом проверки. Новый Assembly Manifest, обязательный универсальный Figma compiler и веб-конструктор этим планом не вводятся.

**Tech Stack:** Node.js 24, JSON Schema, YAML/JSON-compatible contracts/workflow, существующий resolver и renderer CLI, Figma MCP, локальная браузерная проверка.

**Spec:** [master design](../specs/2026-08-24-cupis-structured-email-system-design.md), [HTML rendering design](../specs/2026-09-10-cupis-html-rendering-design.md). Уточнение границ заполняющего модель агента выполняется в пакете 1 до технических изменений.

## Global Constraints

- Persistent source и правки системы — только cloud GitHub. Локальный exact-SHA snapshot допускается только как изолированная среда проверки, а не как источник правок.
- Figma читается только через MCP. Этот план не разрешает изменение дизайна, структуры, названий или Description.
- Данные компонентов не исправляются ради совпадения теста. Доказанное расхождение с Figma повторно проверяется и показывается пользователю; изменение фактов выполняется только после его решения.
- Для воспроизведённого дефекта renderer, workflow или contract owner действует scoped repair из Stage 10 Task 7; факты и HTML-хаки не переносятся в skill.
- Новые письма проходят через модель и renderer. Ручная доводка результата HTML не считается успешным new-build.
- Экспорт и точные format/scale/quality/alpha/crop/display правила берутся из asset contracts и foundation. Существующий MCP-only путь сохраняется.
- Реальные письма, изображения, модели, MCP-ответы и скриншоты не коммитятся в системный репозиторий.
- В папке готовой версии только `email.html` и `images/`; evidence и диагностика находятся снаружи. Исходная версия неизменна, следующая версия увеличивается на `0.1`.
- Тесты и visual regression — локально, делегируются явно `gpt-5.6-terra`, `medium`. Координатор получает краткий итог, не читает полные test logs и не ведёт routine test-fix loops.
- GitHub Actions/PR Checks не запускаются, не читаются и не используются. Если protection технически требует check, сообщить препятствие; не обходить protection.
- Во время реализации — проверки затронутой области. Полный `npm run verify` выполняется перед слиянием на точном финальном коммите кода/контрактов; документационные изменения не требуют полного suite.
- Плановый коммит не начинает реализацию и не разрешает merge. Stage 10 не отмечается завершённым до E2E, merge, exact skill install и clean-chat acceptance.
- Ручной `cupis-active-work-context.md` не обновляется без отдельной просьбы пользователя.

## Пакет 2. Описать и подключить точное заполнение модели

**Зависимость:** пакет 1. **Результат:** исполнитель получает все правила заполнения из одного resolved bundle.

- [ ] Создать `core/email-model-assembly-standard.md` с правилами ниже; зарегистрировать source `email-model-assembly-standard` как Core в manifest и подключить к email workflow шагам inspect/resolve/build-model и design-dependent продолжению. Read-only/technical режимам не добавлять обязательного Figma-запроса.
- [ ] Описать root: один конкретный Email/Template, его контентный слот и фактический порядок блоков. Вложенные cards/items/buttons остаются внутри владельцев. Повторения одного компонента получают разные instance IDs и сохраняют свой контент.
- [ ] Описать pairing: сопоставлять экземпляры двух версий по подтверждённой роли/структуре, не только по порядковому номеру или имени. Различные element IDs в двух contracts не склеивать по типу компонента; несколько одинаковых дочерних элементов нельзя переставить или объединить.
- [ ] Для каждого элемента явно сопоставить model `component_id`, `element_id`, `slot_id` с зарегистрированным контрактом. Заполнять `property_values`, `content_values`, `slots`, `nested_components`, `asset_files` в форме текущей schema.
- [ ] Применять `scope: all` только когда связь и значение действительно одинаковы в обеих версиях. Иначе записывать отдельные Mobile/Desktop bindings; проверить допустимость конкретного element ID в каждом scope.
- [ ] Переносить текст точно, включая значимые пробелы и переносы. Не превращать мягкий визуальный перенос строки в явный перевод строки. Rich text с неподдерживаемой семантикой не уплощать молча: показать неподдерживаемую часть и владельца необходимого исправления.
- [ ] Переносить фактические boolean/property states, включая `false`, и подтверждать effective visibility. Отсутствие значения не считать выключенным состоянием. Скрытое поддерево обрабатывать по действующим model/contract правилам, не включать его для удовлетворения теста.
- [ ] Ссылки сохранять из пользовательских данных/макета. Отсутствующие адреса и alt обрабатывать по существующей политике; не выдавать придуманное значение за извлечённое из Figma. В evidence различать Figma, явный user input и разрешённый policy-derived input.
- [ ] По assets сохранять связь конкретного экземпляра с owner, export boundary и результирующим файлом. Разные переопределённые картинки одного компонента не дедуплицировать по `component_id`. Один общий Desktop asset использовать для двух viewport только по разрешённому контракту.
- [ ] Геометрию, цвет, шрифт, отступы и responsive behavior брать из разрешённых контрактов. Обнаруженный instance override, не выражаемый текущими contracts/properties, показывать как расхождение; не добавлять произвольные CSS overrides и не менять контракт незаметно.
- [ ] Определить временную таблицу трассировки: JSON pointer поля модели → Figma file/node/property или text range и viewport → фактическое значение; для user/policy inputs указывать соответствующий источник. Это verification evidence, не альтернативная модель и не часть папки результата.
- [ ] Проверить, что новый Core действительно попадает в возвращаемый bundle и не требует самостоятельного поиска по памяти. Добавить targeted assertion получения source и сохранения тонкой границы skill.

**Проверка:** другой исполнитель из чистого контекста на одном зарегистрированном блоке с текстом, переключателем и изображением заполняет валидную модель и объясняет источник каждого значения. Точные component facts не дублируются в Core/skill.

**Следующий пакет:** доказать, что ошибочный перенос обнаруживается до визуальной проверки.

## Пакет 3. Проверить перенос данных и исправить доказанные пробелы

**Зависимость:** пакет 2. **Результат:** проверяется одновременно корректность структуры и соответствие источнику.

**Существующие интерфейсы:**

```js
prepareEmailBuildHandoff({ repoRoot, model, candidates, assetEvidence, assetRoot });
executeEmailBuildHandoff({ outputDir, resolution, ...handoffInput });
```

Первый проверяет передачу модели; второй вызывает renderer CLI. Никакая новая проверка не должна подменять эти входы придуманными фактами или сама писать HTML.

- [ ] Взять минимальную пару поддеревьев из свежего MCP-чтения предоставленных писем. Собрать временную модель, candidates и реальные asset receipts; сначала запустить существующую schema/semantic/handoff проверку.
- [ ] Отдельно сопоставить текст, свойства, порядок и owner assets модели с исходными MCP-ответами, а не с expected-данными, построенными из той же модели. Проверить полноту выборки: все читаемые страницы/дочерние узлы получены, обрезанный ответ не считается полным.
- [ ] Выполнить отрицательные сценарии из таблицы. Программные протокольные fixtures могут быть синтетическими, но не называются live Figma evidence. Пользовательские реальные MCP dumps не коммитить.

| Намеренная ошибка | Требуемый результат |
|---|---|
| Пропущен обязательный текст или asset | Typed diagnostic с instance/element path до рендера |
| Текст заменён другим валидным текстом | Source comparison показывает точную разницу; schema pass не объявляется fidelity pass |
| `Show …: false` заменён на `true` | Source comparison показывает несовпадение свойства и viewport |
| Два одинаковых блока переставлены | Несовпадение correspondence/order, даже если schema валидна |
| Перепутаны изображения двух экземпляров | Несовпадение export owner/instance, даже при существующих файлах и валидных hashes |
| Вложенная карточка поднята в слот письма | Placement diagnostic |
| Одинаковый дочерний тип встречается дважды | Два независимых binding без потери/обмена контентом |
| Mobile/Desktop имеют разные element IDs | Обе версии заполняются без коллизий и потери связей |
| Значение с `scope: all` применено к одностороннему element ID | Выявляется отсутствие связи в другой версии; не принимать проверку только одной стороны |
| Неподдерживаемое inline-форматирование или структурное отличие | Явный diagnostic, без уплощения и догадки |
| Evidence отсутствует или относится к другой версии входов | Перенос не считается подтверждённым |

- [ ] Разделить обнаружения: отсутствует инструкция; отсутствует проверка; недостаточна schema model; defect renderer; mismatch component contract. Фиксировать reproduction и фактический owner каждого исправления.
- [ ] Для подтверждённого code defect сначала добавить failing test, затем минимальное исправление и focused rerun через Terra. Для отдельного source-check helper заранее определить точный интерфейс в scoped repair: принимает model, исходные MCP readings, correspondence и разрешённые user/policy inputs; возвращает field-level diagnostics; не принимает ручной `passed: true` вместо сравнения.
- [ ] Не объявлять source-check абсолютной защитой от неверного MCP-извлечения. Проводить независимый re-read спорных узлов и визуальный gate. Hash подтверждает байты изображения, но сам по себе не доказывает правильный source owner.
- [ ] Запустить focused набор для изменённых владельцев. Базовая выборка, если затронуты handoff/model:

```powershell
node --test tests/skills/email-build-handoff.test.mjs tests/rendering/email-model.test.mjs tests/rendering/email-output.test.mjs
```

При source delivery changes добавить `tests/skills/skill-context.test.mjs` и `tests/skills/email-build-skill-boundary.test.mjs`; не запускать весь suite после каждой правки.

**Критерий выхода:** корректная модель проходит, перечисленные намеренные ошибки обнаруживаются соответствующим gate; оставшиеся реальные несовместимости зарегистрированы и устранены в владельцах до полного E2E. Новую schema версию вводить только если доказана необходимость менять представление, с синхронизацией consumers и tests.

**Следующий пакет:** две полные сборки по пользовательским ссылкам.

## Будущий сайт: что сохраняем сейчас

Общий вход рендера остаётся `email-model`. Текущий Figma-путь заполняет его через MCP и проверку соответствия. Будущий сайт сможет формировать модель из выбора блоков, текста, properties и images. Его сохранённый документ, storage, upload-процесс, внешние providers и редактирование версий проектируются отдельно.

Существующие model и renderer не объявляются полностью готовым API веб-конструктора: нынешний orchestration требует Figma MCP asset evidence, а model сейчас временная. При работе над сайтом потребуется отдельный вход/проверка происхождения assets и persistence policy. Эти ограничения не требуют сейчас второго формата композиции, снятия MCP-проверки или скрытой активации upload provider.
