# Banner/Inline: план полной области клика

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This document does not authorize implementation.

**Goal:** Сделать всю адаптивную `content-area` баннера кликабельной по одному адресу, сохранив дизайн и живой текст.

**Architecture:** Сначала проверить отдельный образец одной ссылки, владеющей всей `content-area`. Только после подтверждения способа в требуемых почтовиках перенести его в узкую ветку рендерера и изменить два поля действия в контракте. Внутренняя CSS-раскладка пока является кандидатом.

**Tech Stack:** Node 24, существующий интерпретатор контрактов, HTML/CSS, локальные проверки геометрии и кликов, внешний результат почтовой проверки.

**Spec:** [Требования и результаты исследования](../specs/2026-10-12-banner-inline-click-area-research.md).

**Статус:** сохранено исследование; образец не подготовлен, клиентская совместимость не подтверждена. Этот PR содержит только документацию. Пункты ниже не выполнены и запускаются после отдельного задания.

## Global Constraints

- Вся `content-area`, включая внутренние отступы и промежутки, ведёт по одному адресу; внешние отступы находятся вне ссылки.
- Текст остаётся живым и берётся из письма; дизайн, изображения и соответствие исходным узлам сохраняются. Макеты Figma не меняются.
- Ширина текста адаптивна, высота зависит от содержимого. Reference-размеры не становятся принудительными размерами произвольного экземпляра.
- Подтверждение требуется для Яндекс Почты, Mail.ru и Gmail с указанием реально проверенных веб/мобильных клиентов. Неизвестный результат не считается PASS.
- Полученные письма, изображения и клиентские отчёты остаются локальными. Никакого обязательного доступа или автоматизации всей цепочки Альткрафта.
- Код и визуальные регрессии проверяются локально; GitHub используется для исходников и PR. Исполнители и проверяющие сохраняют выбранную пользователем модель; навык выбирает только поддерживаемое усилие.

## Review Focus

- Узкая ширина и длинный текст: колонки сохраняют порядок, текст переносится, высота растёт, переполнения нет.
- Пустые участки: внутренние отступы, промежутки и незанятая часть колонки остаются кликабельными; внешние отступы не кликабельны.
- Скрытые части: ширина освобождается, лишние промежутки исчезают, скрытые изображения и ссылки не запрашиваются.
- Разные Mobile/Desktop-экземпляры: сохраняется существующий выбор версии, видимость и связывание URL.
- Обработка почтовиком: исходный браузерный результат не подменяет проверку полученного письма и нажатий.

## Этап 1. Подтвердить способ на отдельном образце

**Файлы:** образец и отчёты в отдельной локальной папке вне репозитория; рабочие файлы системы не меняются.

**Вход:** spec, закреплённые Mobile/Desktop-контракты `banner-inline`, исходные изображения и доступные почтовые клиенты.

**Результат:** принятый точный HTML/CSS с его SHA256 и отчётами либо явное отсутствие подтверждения. Только принятый результат является входом этапа 2.

- [ ] Подготовить одну ссылку внутри внешней ячейки: фон, радиус и padding принадлежат ссылке; изображения и текст находятся внутри; внешние отступы снаружи.
- [ ] Проверить кандидат CSS-таблицы на `span` без `calc()`: фиксированные колонки изображений и промежутков, адаптивная текстовая колонка, естественная высота. Не использовать вложенные ссылки и HTML-таблицу внутри ссылки.
- [ ] Локально проверить обе версии, ширины 320/360/600 px, короткий текст, текст в 3 и 6 строк и явные переносы. Сверить типографику, расположение, размеры, рост высоты и область клика с требованиями.
- [ ] После отдельного разрешения на отправку получить результаты для веб, Android и iOS каждого из трёх сервисов. Зафиксировать фактически доступные версии; непроверенные сочетания отметить как `not-run`.
- [ ] В полученном письме проверить переход по внутренним отступам, промежуткам, текстовой колонке и изображениям; убедиться в отсутствии перехода снаружи. Собрать сведения, перечисленные в spec; одного скриншота недостаточно.
- [ ] Принять точный вариант только при сохранении требований во всей согласованной матрице. Если подтверждения нет или требуется другая раскладка, сохранить результат исследования и остановиться до уточнения способа; этап 2 не начинать.

## Этап 2. Перенести подтверждённый способ в систему

**Файлы:**

- Изменить `data/components/marketing.yaml`: только Mobile/Desktop `banner-inline → root-content-area.action.kind` на существующий `whole-element`.
- Изменить `scripts/lib/email-interpreter.mjs`: узкая ветка формирования всей области перед общей обработкой `cellFor()`/`wrapAction()` в `renderShellNative()`.
- Проверки: `tests/rendering/renderer-contract-semantics.test.mjs`, `tests/rendering/email-instance-visibility.test.mjs`; добавить реальные fixtures `banner-inline` и проверки геометрии/кликов в локальный visual harness.

**Вход:** принятый HTML/CSS и отчёты этапа 1, текущие подготовленные узлы, `href`, viewport, facts и HTML видимых дочерних элементов.

**Результат:** одна ссылка на каждый реально выводимый viewport-поддерево `content-area`, естественная высота, сохранённые исходные тексты и изображения, либо диагностика неподдерживаемой структуры без потери содержимого. Точная внутренняя сигнатура новой функции определяется при фиксации принятого варианта этапа 1, до начала программирования.

- [ ] Перезакрепить актуальный SHA системы; сравнить затронутые источники с исследованной версией. Уточнить границу изменения по принятому образцу.
- [ ] Добавить проверки реального Banner/Inline: одна ссылка на выводимое viewport-поддерево, тот же обязательный URL, padding/фон/радиус на области ссылки, отсутствие вложенных ссылок и клика снаружи.
- [ ] Делегировать локальный запуск этих проверок и убедиться, что текущее поведение выявляется как неполная область клика.
- [ ] Добавить отдельную ограниченную обработку подтверждённой структуры; переиспользовать существующие primitives и подготовку видимости. Общую обработку других кнопок сохранить. Не переносить flattening из `inlineActionParts()` без проверки сохранения всех дочерних обёрток и текстового оформления.
- [ ] Изменить два поля `action.kind`. Сохранить `href` slot, узлы, assets, geometry/typography facts, source correspondence и текущие правила переключения Mobile/Desktop. Форма ссылок и модель уже поддерживают нужный URL; менять их без установленной необходимости не требуется.
- [ ] Проверить скрытую `content-area`, каждый скрытый дочерний элемент, единственный оставшийся элемент и различающуюся видимость Mobile/Desktop: без лишних gaps, скрытых ассетов и вопросов о ссылках.
- [ ] Делегировать сравнения геометрии и кликов: иконки и стрелка фиксированы, текст занимает оставшееся место, высота растёт от текста. Reference-контроль: Mobile root 328 → area 296 → текст 166 px; Desktop root 600 → area 552 → текст 384 px. Не фиксировать эти ширины для остальных размеров.
