## Главный принцип области изменений

Сначала классифицируй задачу. До любой записи явно назови:

1. какие объекты разрешено изменить;
2. какие свойства или части файлов разрешено изменить;
3. какие зависимые источники потребуется синхронизировать;
4. что должно остаться без изменений.

Если новое действие расширяет согласованную область, отдельно запроси разрешение. Не считай полезное сопутствующее улучшение автоматически разрешённым.

## Классификация задач

| Тип задачи | Разрешено | Не разрешено без отдельного запроса |
|---|---|---|
| Аудит, консультация, заключение | Чтение файлов и Figma, диагностические проверки, выводы | Любые изменения |
| Description-only | Изменить только явно перечисленные description-поля и синхронизировать реестр | Геометрия, слои, variants, definitions/settings properties, bindings, HTML и assets |
| Изменение Figma-дизайна | Изменить только явно названные узлы и свойства | Unrelated-компоненты, локальные письма и документация вне обязательной синхронизации |
| Создание или naming-изменение Figma-объекта | Применить naming standard к новым или явно разрешённым объектам; синхронизировать затронутые фактические ссылки | Автоматическая миграция legacy- или unrelated-объектов |
| Обновление реестра | Привести конкретные записи в точное соответствие с Figma descriptions | Переписывать descriptions, naming standard или глобальную инструкцию без причины |
| Обновление инструкции | Добавить или уточнить действительно глобальное правило | Параметры, названия и исключения отдельного компонента |
| Сборка нового письма | Использовать инстансы, инструкцию и реестр; создать HTML и assets в папке письма | Менять библиотеку Figma и core-файлы без отдельной задачи |
| Изменение готового письма | Менять только прямо запрошенные HTML/assets | Figma, реестр, инструкцию и другие письма без отдельной причины |

Фраза пользователя «только описание», «локальный файл не трогай», «HTML не правим» или аналогичное ограничение является жёсткой границей задачи.

## Основной рабочий цикл

1. Прочитать актуальные файлы по каноническим путям, указанным в разделе «Активный комплект».
2. Классифицировать задачу и определить точную область изменений.
3. Открыть только необходимые Figma-узлы или локальные файлы.
4. Зафиксировать исходное состояние изменяемых объектов.
5. Выполнить минимальное точечное изменение.
6. Синхронизировать только обязательные зависимые источники.
7. Провести фактическую проверку результата и unrelated-объектов.
8. Обновить этот чек-пойнт только при изменении процесса, состава комплекта или действующего статуса библиотеки.

## Работа с Figma

### Точечное чтение

- Не проводить повторный полный аудит библиотеки, если достаточно конкретного узла и актуального реестра.
- Полный скан Marketing и Service roots выполнять только для утверждения уровня «нигде», «во всех компонентах» или «в библиотеке больше нет».
- Для проверки конкретного компонента читать его variants, актуальные значения, variable bindings и description.

### Доказательство фактов structured contract

Если задача касается точности structured component contract, для каждого компонента отдельно получить свежие Mobile/Desktop-данные через Figma MCP, используя проверенный read-only capture-профиль `scripts/figma/capture-contract-source.js`. Это включает реальные тексты, типографику, размеры, padding/gaps, цвета/fills, bindings, properties и структуру; скриншот — только дополнительная визуальная проверка. Затем запустить `scripts/audit-figma-contract-facts.mjs` с точным component ID и этим пакетом. Связи Figma-полей с contract-полями берутся только из `contracts.figma_fact_links` канонического component record, а не из переданного при запуске файла. Любой uncovered, несовпавший или не имеющий прямого Figma provenance факт оставляет компонент непроверенным. Метка статуса и legacy Markdown не отменяют эту проверку. До разрешения расхождения не выдавать component contract за доказанный источник истины.

### Перед изменением

Для каждого затрагиваемого узла сначала определить текущую и предполагаемую смысловую роль:

- production component — самостоятельный смысловой блок, который нужно реализовать в HTML;
- root shell — корневая оболочка письма, которая задаёт реальную структуру HTML и содержит дочерние блоки;
- assembly template — сборочный шаблон письма; его собственная оболочка реализуется, а Slot или вложенные блоки дополняют её;
- example — демонстрационный инстанс, не являющийся отдельным контрактом вёрстки;
- export asset — владелец экспортируемого изображения.

Отдельно зафиксировать, участвует ли сам узел в HTML и дополняет ли Slot его оболочку или заменяет её. Если роль нельзя определить однозначно либо изменение переводит узел в другую роль, остановиться после чтения и запросить отдельное разрешение.

До записи составить mutation allowlist: точные Figma-объекты, поля и операции, которые разрешено изменить. Связанные descriptions компонента, component properties и Slot, а также ссылки реестра сначала только проверить; изменять их можно лишь при включении точного metadata-поля в allowlist.

Зафиксировать structural fingerprint каждого затрагиваемого узла:

- `id`, `name`, `type` и parent `id`;
- упорядоченный список `id`, `name` и `type` непосредственных children;
- width/height, Auto Layout mode, alignment, padding и gap;
- variant keys и values;
- component-property keys, types, defaults, descriptions и settings;
- variable bindings, instance/property references и Slot bindings;
- для spacing-задач — фактические padding/gap и имена bound variables.

Поля, прямо включённые в mutation allowlist, фиксируются для сравнения до → после; все остальные части fingerprint считаются неизменяемыми.

### Description-only

- По умолчанию присваивать только `node.description`.
- Description component property или Slot является отдельным metadata-полем: его можно записывать только если точный property key включён в mutation allowlist.
- Перед записью проверить связанные component-property и Slot descriptions на противоречащий контракт. Конфликт вне allowlist сообщить, но не исправлять автоматически.
- Новую формулировку `не реализовывать`, `не верстать`, `не экспортировать` или `игнорировать` добавлять только после доказательства смысловой роли узла. Не описывать root shell или assembly template как не участвующий в HTML, если его оболочка должна быть реализована.
- Не нормализовывать, не переименовывать и не перестраивать компонент.
- После записи повторно прочитать все разрешённые description-поля.
- Сравнить structural fingerprint с исходным состоянием.
- Проверить служебное экранирование HTML-подобных токенов, чтобы `&lt;...&gt;` не превратилось в двойное `&amp;lt;...&amp;gt;`.
- В той же задаче обновить соответствующую запись реестра.

### Изменение дизайна

- Требует прямого запроса пользователя.
- Перед изменением отдельно назвать узлы, операции и свойства в mutation allowlist.
- Изменение смысловой роли, типа узла, hierarchy, Slot-модели или component properties требует отдельного явного разрешения, даже если оно кажется необходимым продолжением дизайна.
- После изменения сравнить visual geometry, variants, bindings и полный structural fingerprint.
- Description обновлять только если изменился контракт вёрстки компонента и точное metadata-поле включено в allowlist.
- После изменения description синхронизировать реестр.

### Нейминг

Naming standard применять обязательно при создании, переименовании или структурной переработке компонента, property, смыслового слоя или asset owner, а также при полном naming-аудите.

- Новый объект должен соответствовать стандарту до завершения задачи.
- Для существующего расхождения в разрешённой области сначала показать точное сопоставление old → new и зависимые обновления.
- Если rename прямо не разрешён, не менять имя: запросить разрешение либо оставить диагностическое замечание.
- Legacy-объекты вне области задачи не менять и не использовать как основание для расширения аудита.
- Description-only не превращать в naming-миграцию.
- Разрешение на rename относится только к согласованным old → new именам. Оно не разрешает Component ↔ Frame conversion, создание или удаление property/Slot, reparenting, изменение hierarchy, Auto Layout, geometry, variants или bindings.
- При переименовании asset owner сохранять исходный @2x или @4x; изменение scale требует отдельного export-contract запроса.
- После записи повторно прочитать names, properties и children; проверить Mobile и Desktop, затронутые ссылки, реестр и отсутствие unrelated-изменений.

### Проверка после записи

- После последней Figma-записи выполнить отдельный read-only re-fetch затронутых узлов и их непосредственных родителей; не совмещать эту проверку с новой записью.
- Для каждого разрешённого поля подтвердить ожидаемое значение до → после.
- Для всех остальных частей structural fingerprint подтвердить точное совпадение.
- Повторно проверить связанные component-property и Slot descriptions, даже если они не изменялись.
- Любой unexpected diff считать остановкой задачи. Зафиксировать различие и сообщить пользователю; не расширять mutation allowlist задним числом и не пытаться автоматически исправить побочное изменение.

| Изменены геометрия или структура компонента | Проверить description; при изменении контракта обновить его и реестр | Глобальную инструкцию без глобального основания |
| Изменён конкретный padding, gap, размер или asset компонента | Обновить его description и реестр, если это влияет на вёрстку | Инструкцию и чек-пойнт |
| Создан или переименован компонент, property, смысловой слой или asset owner | Проверить naming standard; обновить фактические имена/variants в реестре и только реально затронутые ссылки Description | Массовую миграцию библиотеки, глобальную инструкцию и unrelated-компоненты |
| Изменён naming standard | Обновить ссылки комплекта и routing навыка, если изменились путь или процесс; не мигрировать существующие компоненты автоматически | Реестр, Figma и descriptions без отдельной migration-задачи |
| Изменено глобальное правило всех писем | Обновить инструкцию; при изменении процесса обновить чек-пойнт | Descriptions отдельных компонентов без необходимости |
| Изменён реестр без Figma-записи | Сначала доказать, что реестр отставал от Figma | Не считать реестр новым источником истины |
| Изменён HTML или assets готового письма | Проверить только затронутое письмо и его ссылки | Figma и core-документацию без отдельной причины |
| Изменился состав или путь core-файлов | Обновить раздел «Активный комплект» | Компонентные правила |

## Граница между инструкцией, naming standard и descriptions

В глобальной инструкции допустимы:

- правила всего HTML-документа;
- общая адаптивность и совместимость email-клиентов;
- глобальные контракты изображений и экспорта;
- общие требования проверки и доступности;
- единые правила внешнего ритма и размещения scope-типов.

В naming standard должны оставаться только универсальные naming-константы, контролируемый словарь, правила классификации и алгоритм проверки. Не переносить туда перечень текущих компонентов, IDs, descriptions, геометрию, значения или компонентные исключения.

В descriptions и реестре должны оставаться:

- структура конкретного компонента;
- его Mobile/Desktop-композиция;
- точные внутренние padding, gaps и размеры;
- точные export boundaries и display-размеры его assets;
- компонентные исключения и fallback.

Не добавлять в глобальную инструкцию перечни конкретных компонентов, их внутренние значения или напоминания о прежних ошибочных состояниях.

## Проверенные анти-паттерны

- Изменять структуру или организацию Figma-компонента, когда запрошено только description.
- Добавлять компонентное значение или исправление единичного случая в глобальную инструкцию.
- Смешивать внешний root/inset с внутренним content padding.
- Делать вывод о токене по числовому значению без проверки variable binding.
- Утверждать отсутствие binding после проверки только одного компонента или одной библиотеки.
- Доверять старому description после изменения дизайна без проверки фактической геометрии.
- Обновлять Figma-description и забывать реестр.
- Дублировать фактический состав библиотеки или component contracts в naming standard.
- Использовать naming standard как разрешение массово переименовать legacy-компоненты.
- Считать rename разрешением изменить type, properties, Slot, hierarchy или layout узла.
- Добавлять негативную инструкцию о вёрстке без подтверждения смысловой роли узла.
- Удалять или менять @2x/@4x при обычном переименовании asset owner.
- Повторно исследовать всю библиотеку, когда достаточно точечного чтения.
- Править HTML или assets в задаче, ограниченной Figma и документацией.
- Добавлять «полезные» правила или перестраховки, которых не требует задача.
- Сообщать об успешной проверке без свежего фактического результата.

## Когда обновлять этот чек-пойнт

Обновлять файл, только если:

1. изменился общий рабочий процесс;
2. изменились состав или расположение файлов комплекта;
3. изменился действующий инвариант библиотеки, необходимый в следующих задачах;
4. обнаружен повторяющийся анти-паттерн, который нельзя надёжно предотвратить инструкцией или description.

Обычное изменение description одного компонента не требует обновления чек-пойнта, если процесс и общие инварианты не изменились.

- [ ] Namespace, component pattern, properties и структурные слои проверены по naming standard.
- [ ] Одинаковые смысловые layers совпадают между Mobile и Desktop.
- [ ] Повторяемые siblings и asset owners названы однозначно.
- [ ] Исходные @2x/@4x сохранены; изменение scale не выполнено без отдельного запроса.
- [ ] Generic-, visual-, HTML- и viewport-зависимые имена не добавлены.
- [ ] Rename не использован как разрешение менять type, hierarchy, properties, Slot, layout, geometry, variants или bindings.
- [ ] Реестр и ссылки Description обновлены только там, где изменился фактический объект.
- [ ] Legacy- и unrelated-объекты не изменены.
- [ ] Отдельный read-only re-fetch подтвердил согласованные names и неизменность остального structural fingerprint.

## Чек-лист: обновление инструкции

- [ ] Правило действительно глобальное, а не компонентное.
- [ ] Оно не дублирует description или реестр.
- [ ] Оно не содержит перечня текущих компонентов.
- [ ] Оно не фиксирует старое ошибочное состояние как отдельный запрет без необходимости.
- [ ] Проверены возможные противоречия с существующими глобальными правилами.
- [ ] Изменения ограничены необходимыми разделами инструкции.
- [ ] Чек-пойнт обновлён только при изменении процесса или инварианта.

## Чек-лист: синхронизация реестра

- [ ] Используется актуальный Figma-description.
- [ ] Node ID и variant list относятся к правильному component set.
- [ ] Текст description совпадает после нормализации перевода строк.
- [ ] Старые значения в записи отсутствуют.
- [ ] Другие записи реестра не изменены без основания.
- [ ] Дата слепка обновлена только после реальной синхронизации.

## Чек-лист: HTML и assets

- [ ] Пользователь разрешил изменение конкретного письма.
- [ ] Использованы актуальная инструкция, реестр и конкретные инстансы.
- [ ] Изменены только запрошенные HTML/assets.
- [ ] Все локальные `src` существуют и ведут на актуальные файлы.
- [ ] Mobile/Desktop используют общие assets согласно инструкции и descriptions.
- [ ] Пропорции, crop и прозрачность проверены по соответствующему контракту.
- [ ] Выполнены обязательные viewport- и render-проверки инструкции.
- [ ] Figma и core-документация не изменены без отдельной причины.

## Финальная проверка любой задачи

- [ ] Фактический результат проверен отдельным read-only чтением после последней записи.
- [ ] Unexpected diff отсутствует; при его наличии задача остановлена без автоматического расширения области.
- [ ] Все обязательные зависимые источники синхронизированы.
- [ ] Naming standard применён только в предусмотренных им режимах.
- [ ] Старые значения или ссылки больше не используются.
- [ ] Область изменений совпадает с запросом пользователя.
- [ ] Unrelated-файлы, Figma-узлы и дизайн не изменены.
- [ ] Итоговый ответ перечисляет только реально выполненные действия и проверки.
